每次修改一行代码都重新安装全部依赖，构建会很慢；但过度依赖缓存又可能隐藏依赖变化。Dockerfile 的层顺序应配合文件变化频率设计。

构建指令与相关输入共同影响缓存是否可复用。先复制依赖清单再安装，最后复制业务代码，可以隔离变化；构建缓存与运行数据不是同一个存储层。

![Docker 镜像构建：依赖层、缓存与运行产物：处理路径与验证条件](/img/tech-notes/docker-image-cache-build.svg)

## 一、问题的范围与前提

镜像、容器、网络和数据卷是不同对象。镜像定义运行产物，容器执行进程，网络决定可达关系，卷管理跨容器生命周期的数据。把它们分别列出来，有助于判断重建究竟改变了什么；单个容器显示 Up，只能说明相关入口进程仍然存在。

## 二、技术分析与方案取舍

COPY 的范围越大，越容易因无关文件变化失去缓存。依赖清单先复制，安装后再复制业务文件，可以让代码改动不影响依赖层。ignore 规则排除本地数据、虚拟环境和凭据，最终镜像再检查运行资源是否齐全。基础标签可能重建，严格复现需摘要；构建缓存提升效率，但不能证明当前依赖与目标 CPU 架构相容。

先固定基础镜像、应用版本和必要配置，再检查最终容器的实际参数。Compose 文件只是期望描述，已经创建的容器可能仍带旧环境。涉及端口、设备和挂载等创建参数时，需要按差异重建；普通 restart 不会重新读入全部创建配置。重建前确认数据所在位置和现有卷身份。

## 三、实现与排查的顺序

1. 区分依赖和业务文件。
2. 固定基础镜像及依赖范围。
3. 减少无关文件进入构建上下文。
4. 检查最终镜像实际内容。

按这个顺序保留中间结果，可以区分输入条件、处理过程和最终输出。前一阶段的条件不成立时，先解释对应错误，再继续后面的试验；单次返回成功不足以覆盖整条链路。

### 最小示例

```dockerfile
FROM python:3.7.6-slim-buster
WORKDIR /app
COPY requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py ./
```

此片段展示依赖层与业务层分离，不是完整运行入口。基础镜像和依赖应按目标日期与平台选择，复制的文件需真实存在。构建上下文通过忽略规则排除凭据、数据与无关产物。

## 四、验证和结果解释

可以将配置解析结果、容器实际状态和一次业务请求放在一起观察。配置有效说明语法和部分引用成立，镜像构建有效说明产物生成，真实请求才进一步说明依赖链可用。将这些结果分开记录，能避免一个阶段的成功遮住另一个阶段的失败。

| 需要验证的结果 | 保留的对照 | 不能由此推出的结论 |
| --- | --- | --- |
| 代码变化不必重做不变依赖 | 固定输入与配置、对应输出 | 一次成功代表所有条件成功 |
| 依赖清单变化会正确使缓存失效 | 中断前后状态与错误阶段 | 没有报错代表结果正确 |
| 产物不包含凭据和无关数据 | 恢复后的同条件复测 | 临时恢复代表根因已经消失 |

容器异常不一定需要重建整套服务。先定位受影响对象，再确认是否有状态需要保留。数据卷独立于容器并不等于有独立备份，健康检查也不等于自动重启。恢复策略需要与退出、网络失联、数据损坏等具体条件对应。

## 五、适用边界与结论

缓存命中不证明依赖仍适合目标平台。主机 CPU 架构和二进制扩展需要匹配，不能把本机虚拟环境直接复制进异构镜像。

这条路径把“区分依赖和业务文件”与“检查最终镜像实际内容”连在一起，中间保留可复查的条件。实施时优先确认“代码变化不必重做不变依赖”，再检查“产物不包含凭据和无关数据”；两者都满足，才能在当前样本与配置范围内评价方案。设备、数据或软件版本改变以后，相关假设需要重新验证。
