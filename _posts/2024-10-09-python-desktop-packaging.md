脚本可运行，打包后资源缺失或依赖不符，说明运行环境改变。

打包器组织解释器与资源，临时展开位置、工作目录和动态库影响路径。用户可写配置与程序资源应分离。

![Python 桌面打包：运行路径、资源与依赖：处理路径与验证条件](/img/tech-notes/python-desktop-packaging.svg)

## 一、问题的范围与前提

解释器、依赖、进程与任务状态是不同层次。代码能在一个目录执行，不表示服务或另一个虚拟环境使用相同模块。文件路径、导入来源和并发对象生命周期需要明确，尤其在多进程、长时间运行与异常重试中。

## 二、技术分析与方案取舍

打包后的工作目录可能由用户启动位置决定，资源路径应根据程序产物定位，可写配置放用户允许位置。动态库、图形依赖和系统驱动不能只由开发机环境推断。干净目标机器测试启动、保存配置与路径空格，记录构建脚本和资源清单。跨平台在各自环境构建验证，不能仅改文件扩展名。

输入解析和业务处理之间建立明确边界，失败不默默变成默认成功值。使用标准库管理文件、队列与异常时，核对具体版本行为。外部副作用具有稳定身份，资源在正常与异常出口都被回收；共享可变对象只在明确同步与归属条件下使用。

## 三、实现与排查的顺序

1. 盘点资源与动态依赖。
2. 区分只读和可写路径。
3. 测试干净机器。
4. 保存构建配置。

按这个顺序保留中间结果，可以区分输入条件、处理过程和最终输出。前一阶段的条件不成立时，先解释对应错误，再继续后面的试验；单次返回成功不足以覆盖整条链路。

### 最小示例

```bash
python -V
python -m pip --version
uname -m
cmake --version
c++ --version
free -h
```

这些查询分别检查解释器、安装工具、架构、工具链与内存。安装日志确认真实阶段以后，再决定处理下载还是编译。构建活动与最终导入验证不能被等待时长代替。

## 四、验证和结果解释

记录解释器来源、必要版本和最小复现输入，再保存有效错误链。安装失败按下载、构建、链接与导入阶段分析，执行失败按输入、资源和结果归属分析。公开示例使用通用路径与虚构业务对象，不输出个人环境或原始附件。

| 需要验证的结果 | 保留的对照 | 不能由此推出的结论 |
| --- | --- | --- |
| 无开发环境可启动 | 固定输入与配置、对应输出 | 一次成功代表所有条件成功 |
| 路径空格中文正常 | 中断前后状态与错误阶段 | 没有报错代表结果正确 |
| 配置更新不丢失 | 恢复后的同条件复测 | 临时恢复代表根因已经消失 |

验证包括格式错误、资源不可用、任务取消与进程重启。并发提升要同时检查吞吐、尾延迟、内存与错误，不能只增加 worker 数量。文件发布、数据库提交和业务动作仍有各自原子性边界，需要分别确认。

## 五、适用边界与结论

打包成功不保证所有平台，跨系统产物需要在对应目标环境验证。

这条路径把“盘点资源与动态依赖”与“保存构建配置”连在一起，中间保留可复查的条件。实施时优先确认“无开发环境可启动”，再检查“配置更新不丢失”；两者都满足，才能在当前样本与配置范围内评价方案。设备、数据或软件版本改变以后，相关假设需要重新验证。
