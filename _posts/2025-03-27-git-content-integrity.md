正文构建后变化而内容包仍绑定旧摘要，会让状态与读者看到的内容不同。

摘要识别原始字节变化，计算应在最终构建后。图片完整解码和引用关系另行检查，旧稿不能盲目绑定新正文。

![文章发布完整性：最终 HTML 哈希与素材：处理路径与验证条件](/img/tech-notes/git-content-integrity.svg)

## 一、问题的范围与前提

接口由请求身份、参数语义、授权条件和结果状态共同构成。HTTP 层成功只描述传输与响应，业务处理还可能处于受理、执行或等待确认阶段。将外部输入转换为内部对象以后，仍需核对类型、范围和当前状态，不能因为 JSON 能解析就直接使用。

## 二、技术分析与方案取舍

完整性校验应基于最后一次构建后的实际 HTML 字节。封面路径、正文和模板变化都可能改变最终文件，因此先构建再计算摘要。内容包保存该摘要与素材清单，校验器比较仓库里的真实文件，而不是比较两个手写字符串。正文更新后不能只批量刷新哈希，必须确认分发稿也对应新内容。

浏览器可访问证明部署的一部分，若取到旧缓存还需要版本对照。哈希相同说明字节相同，不说明文章事实正确，所以它与编辑审核各自承担不同责任。

应用入口应有明确大小、时间和并发预算。正常和异常返回都遵循稳定结构，调用方可以据此选择等待、查询、修正或重试。涉及写入与外部动作时，为同一业务意图提供稳定身份，并在持久化边界内管理已受理结果，防止回执丢失造成重复执行。

## 三、实现与排查的顺序

1. 完成正文素材。
2. 运行构建。
3. 计算最终摘要。
4. 核对引用与线上结果。

按这个顺序保留中间结果，可以区分输入条件、处理过程和最终输出。前一阶段的条件不成立时，先解释对应错误，再继续后面的试验；单次返回成功不足以覆盖整条链路。

### 最小示例

```bash
git status --short
git log -5 --oneline
git rev-parse HEAD
git diff --stat
```

提交标识只说明源码状态，工作区可能还有未提交变化。部署记录还应关联镜像摘要、配置与迁移版本。这里不自动提交或回退，也不把含凭据的配置纳入版本管理。

## 四、验证和结果解释

至少关联请求到达、关键依赖调用和处理结果。日志记录标识与阶段即可，密码、Cookie、token 和原始敏感请求不应进入公共记录。排查时用同一入口比较请求与响应，再结合后端证据，避免页面统一错误文案掩盖具体原因。

| 需要验证的结果 | 保留的对照 | 不能由此推出的结论 |
| --- | --- | --- |
| 哈希匹配最终文件 | 固定输入与配置、对应输出 | 一次成功代表所有条件成功 |
| 图片完整 | 中断前后状态与错误阶段 | 没有报错代表结果正确 |
| 内容版本一致 | 恢复后的同条件复测 | 临时恢复代表根因已经消失 |

验收除了正常返回，还包括重复提交、格式错误、依赖超时与调用方取消。系统应能对未知结果查询或恢复，而不是把每个超时都当成未执行。恢复范围尽量匹配故障，防止一个依赖异常引发所有服务同时反复重启。

## 五、适用边界与结论

哈希不能替代语义核对，失败时先查变化原因再修正。

这条路径把“完成正文素材”与“核对引用与线上结果”连在一起，中间保留可复查的条件。实施时优先确认“哈希匹配最终文件”，再检查“内容版本一致”；两者都满足，才能在当前样本与配置范围内评价方案。设备、数据或软件版本改变以后，相关假设需要重新验证。
