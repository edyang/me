已有 Ed25519 密钥时先确认用途，覆盖同名文件可能影响其它连接。

账号登记公钥，私钥保留本机。主机指纹、账号认证、remote 协议和仓库权限分别验证；HTTPS 不会因 SSH成功自动切换。

![GitHub SSH 配置：已有密钥先核对再复用：处理路径与验证条件](/img/tech-notes/github-reuse-existing-ssh-key.svg)

## 一、问题的范围与前提

单台 Linux 主机上的进程、文件、网络和服务管理有各自边界。排查时先确认当前命令所处的用户、网络命名空间与工作目录，再把进程状态和实际业务请求对应起来。交互终端、系统服务和容器可能同时使用不同环境，即使执行文件名称一样，也不代表访问同一组资源。

## 二、技术分析与方案取舍

已有私钥时先生成或读取对应公钥，检查文件权限和公钥指纹。上传的是 .pub 内容，私钥留在本机。多个账号可以用 SSH Host 别名明确身份，再把仓库 remote 与别名对应；普通用户名提示不能代替实际认证结果。ssh -T 的欢迎信息用于核对账号，GitHub 不提供交互 shell，所以命令退出状态与普通服务器登录不同。

若连接成功仍无法推送，再查仓库权限与 remote 协议。公开笔记只展示通用路径和命令结构，不贴私钥、公钥全文或私人邮箱。

变更应围绕已经定位的条件进行。先保存当前有效配置与一段故障日志，再修改一个变量，使用同一入口复测。服务重启只重新执行当前单元，单元文本改变后还需按管理器规则重新加载；网络配置改变也可能影响已有连接。每一步都应能说明它解决的是地址、权限、环境还是进程生命周期。

## 三、实现与排查的顺序

1. 核对公钥指纹。
2. 确认服务器身份。
3. 指定密钥测试。
4. 检查 remote 与权限。

按这个顺序保留中间结果，可以区分输入条件、处理过程和最终输出。前一阶段的条件不成立时，先解释对应错误，再继续后面的试验；单次返回成功不足以覆盖整条链路。

### 最小示例

```bash
test -f ~/.ssh/id_ed25519.pub && ssh-keygen -lf ~/.ssh/id_ed25519.pub
# 只验证与 GitHub 的身份认证，不输出私钥
ssh -T git@github.com
git remote -v
```

公钥不存在而私钥已存在时，可在本机用 ssh-keygen -y 恢复公钥。上传 .pub 内容，私钥不能上传。remote -v 可能包含私人仓库地址，公开记录应使用通用示例。

## 四、验证和结果解释

进程 PID、监听地址、错误发生时间与退出状态适合形成一组关联证据。单次截图通常不足以解释间歇故障，持续观察可以发现状态转换和重复失败间隔。公开记录只保留必要错误类型与通用路径，认证信息、真实主机名和内部地址不进入文章。

| 需要验证的结果 | 保留的对照 | 不能由此推出的结论 |
| --- | --- | --- |
| 认证输出正确解释 | 固定输入与配置、对应输出 | 一次成功代表所有条件成功 |
| 仓库可访问 | 中断前后状态与错误阶段 | 没有报错代表结果正确 |
| 凭据不被公开 | 恢复后的同条件复测 | 临时恢复代表根因已经消失 |

故障复现时要区分稳定错误和偶发错误。稳定错误优先检查固定配置，偶发错误再看资源峰值、连接状态和时间变化。修复后既测正常路径，也验证启动失败、依赖不可达与重启条件，避免只在已有运行环境中成功。

## 五、适用边界与结论

带口令密钥是否免输入还取决于 agent，非零测试退出码需结合 GitHub 返回内容。

这条路径把“核对公钥指纹”与“检查 remote 与权限”连在一起，中间保留可复查的条件。实施时优先确认“认证输出正确解释”，再检查“凭据不被公开”；两者都满足，才能在当前样本与配置范围内评价方案。设备、数据或软件版本改变以后，相关假设需要重新验证。
