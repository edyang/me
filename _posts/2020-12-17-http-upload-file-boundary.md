上传页面进度到百分之百，只说明客户端发送完毕，服务器仍可能验证失败或尚未处理文件。接口应把传输、接收、处理与结果获取分开。

文件名由外部输入提供，不能直接决定服务器保存路径。扩展名与 MIME 只是线索，实际格式、大小和可解码性需要检查；任务状态必须对应真实持久化结果。

![文件上传接口：内容验证、存储路径与任务状态：处理路径与验证条件](/img/tech-notes/http-upload-file-boundary.svg)

## 一、问题的范围与前提

接口由请求身份、参数语义、授权条件和结果状态共同构成。HTTP 层成功只描述传输与响应，业务处理还可能处于受理、执行或等待确认阶段。将外部输入转换为内部对象以后，仍需核对类型、范围和当前状态，不能因为 JSON 能解析就直接使用。

## 二、技术分析与方案取舍

服务端为文件生成内部对象 ID，原始名字只作为受控显示属性，避免路径穿越和覆盖。上传结束后检查大小、实际格式和完整解码，再进入异步任务。页面应区分接收完成与处理完成，结果链接要受访问权限保护。异常文件和任务取消保留明确状态，不创建空文件后标成功，也不把用户原始内容复制进公开日志。

应用入口应有明确大小、时间和并发预算。正常和异常返回都遵循稳定结构，调用方可以据此选择等待、查询、修正或重试。涉及写入与外部动作时，为同一业务意图提供稳定身份，并在持久化边界内管理已受理结果，防止回执丢失造成重复执行。

## 三、实现与排查的顺序

1. 为上传设置大小和类型范围。
2. 生成内部对象身份与安全路径。
3. 接收完成后验证格式。
4. 异步处理用明确任务状态查询。

按这个顺序保留中间结果，可以区分输入条件、处理过程和最终输出。前一阶段的条件不成立时，先解释对应错误，再继续后面的试验；单次返回成功不足以覆盖整条链路。

### 最小示例

```text
传输中 → 接收完整 → 格式验证 → 处理中 → 结果可取
失败单独保存类型和可恢复范围
```

状态名称表达不同实际动作，前端百分比不是服务端完成。文件内部身份与原始文件名分开，格式完整解码后才进入处理链。

## 四、验证和结果解释

至少关联请求到达、关键依赖调用和处理结果。日志记录标识与阶段即可，密码、Cookie、token 和原始敏感请求不应进入公共记录。排查时用同一入口比较请求与响应，再结合后端证据，避免页面统一错误文案掩盖具体原因。

| 需要验证的结果 | 保留的对照 | 不能由此推出的结论 |
| --- | --- | --- |
| 异常文件不会进入处理链 | 固定输入与配置、对应输出 | 一次成功代表所有条件成功 |
| 同名上传不会覆盖他人数据 | 中断前后状态与错误阶段 | 没有报错代表结果正确 |
| 处理失败能返回可定位原因 | 恢复后的同条件复测 | 临时恢复代表根因已经消失 |

验收除了正常返回，还包括重复提交、格式错误、依赖超时与调用方取消。系统应能对未知结果查询或恢复，而不是把每个超时都当成未执行。恢复范围尽量匹配故障，防止一个依赖异常引发所有服务同时反复重启。

## 五、适用边界与结论

客户端上传进度不是服务端成功率。公开日志去除用户文件名与敏感内容，存储与访问授权还需单独设计。

这条路径把“为上传设置大小和类型范围”与“异步处理用明确任务状态查询”连在一起，中间保留可复查的条件。实施时优先确认“异常文件不会进入处理链”，再检查“处理失败能返回可定位原因”；两者都满足，才能在当前样本与配置范围内评价方案。设备、数据或软件版本改变以后，相关假设需要重新验证。
