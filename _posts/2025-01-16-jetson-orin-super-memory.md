边缘算力提升后，仍需要同时观察显存共享、温度和功耗模式。

统一内存、频率与热限制影响持续吞吐。短时峰值不能代表长时间稳定性能，外设与录像也占资源。

![Orin NX Super 负载预算：功耗、温度与推理：处理路径与验证条件](/img/tech-notes/jetson-orin-super-memory.svg)

## 一、问题的范围与前提

规格、安装与实际工作条件需要分别核对。接口外形相同不证明电气和数据能力相同，标称性能也不代表目标工况。测量基准、单位和容差应明确，再通过受控对照定位问题。

## 二、技术分析与方案取舍

Orin NX 的 Super Mode 需要对应 JetPack 6.2 与支持的刷写配置，不能把 Orin Nano Super 开发套件的发布日期直接当作 NX 支持日期。功耗模式、供电与散热一起影响持续性能；只提高时钟而没有足够散热，长时间运行可能降频。

统一内存还要供 CPU、摄像头缓冲、模型和录像使用，不能将标称容量全部分给推理。测试时固定码流、模型、输入尺寸和并发，持续记录 tegrastats 中的内存、温度与负载。把启动峰值和稳态分别画出来，能发现刚启动很快但长时间不稳定的配置。

最终选择应给通信、采集和系统保留余量，TOPS 指标不直接等于某个模型的帧率。

从允许范围内的只读或低风险验证开始，一次改变一个条件，保留型号规格与必要版本。供电、线材、机械配合和软件配置分开观察。涉及电气维修或设备动作时，按原厂说明与专业操作边界实施，公开文章不复制未核验接线。

## 三、实现与排查的顺序

1. 核对目标模块与模式。
2. 固定代表性输入。
3. 持续观察资源温度。
4. 比较冷启动与稳态。

按这个顺序保留中间结果，可以区分输入条件、处理过程和最终输出。前一阶段的条件不成立时，先解释对应错误，再继续后面的试验；单次返回成功不足以覆盖整条链路。

### 最小示例

```bash
cat /etc/nv_tegra_release
uname -m
uname -r
sudo nvpmodel -q
# 持续观察；按 Ctrl-C 结束
tegrastats
```

这是 Jetson 上的只读环境检查。功耗模式查询需要相应工具；具体模式编号按模组、载板与刷写配置确认。不要直接复制另一台设备的提频设置。

## 四、验证和结果解释

交叉测试使用已知可用部件和独立参考工具，结果记录输入条件、观察与排除范围。单个错误码只提供方向，不能证明唯一故障件。工程尺寸和屏幕显示也要分别核验，漂亮模型不等于实物可以装配。

| 需要验证的结果 | 保留的对照 | 不能由此推出的结论 |
| --- | --- | --- |
| 目标模式不降级失控 | 固定输入与配置、对应输出 | 一次成功代表所有条件成功 |
| 内存有余量 | 中断前后状态与错误阶段 | 没有报错代表结果正确 |
| 外设服务不被挤掉 | 恢复后的同条件复测 | 临时恢复代表根因已经消失 |

检查重启、重插、重复装配与允许工况变化。小步迭代保留对照，避免同时更换多个变量后无法判断原因。目标精度和实际误差分别表达，探索样件、概念演示和已验收设备不使用同一完成口径。

## 五、适用边界与结论

不用标称 TOPS 直接预测实际模型速度，按任务和精度路径测试。

这条路径把“核对目标模块与模式”与“比较冷启动与稳态”连在一起，中间保留可复查的条件。实施时优先确认“目标模式不降级失控”，再检查“外设服务不被挤掉”；两者都满足，才能在当前样本与配置范围内评价方案。设备、数据或软件版本改变以后，相关假设需要重新验证。
