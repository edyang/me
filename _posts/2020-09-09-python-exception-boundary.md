用一个 except 包住整个程序，可以让进程不退出，却也容易让错误数据继续进入后续流程。异常边界应和可恢复的操作范围一致，而不是尽量吞掉所有错误。

网络暂时失败、输入格式错误与程序逻辑缺陷具有不同处理方式。捕获具体异常后，分别决定重试、拒绝或终止；日志保留异常链，调用者获得明确失败结果。

![Python 异常处理：保留错误原因并明确恢复范围：处理路径与验证条件](/img/tech-notes/python-exception-boundary.svg)

## 一、问题的范围与前提

解释器、依赖、进程与任务状态是不同层次。代码能在一个目录执行，不表示服务或另一个虚拟环境使用相同模块。文件路径、导入来源和并发对象生命周期需要明确，尤其在多进程、长时间运行与异常重试中。

## 二、技术分析与方案取舍

例如输入解析 ValueError 可以返回明确的无效输入，而网络超时可能按预算重试；业务状态不相容则不应自动重试。捕获 Exception 后直接继续，会让调用者看不到真正失败，后续还可能使用未初始化变量。清理资源可放在 finally 或上下文管理边界，但清理错误也不能覆盖原始原因。

日志保留最小上下文与异常链，避免输出完整敏感请求。

输入解析和业务处理之间建立明确边界，失败不默默变成默认成功值。使用标准库管理文件、队列与异常时，核对具体版本行为。外部副作用具有稳定身份，资源在正常与异常出口都被回收；共享可变对象只在明确同步与归属条件下使用。

## 三、实现与排查的顺序

1. 按操作范围捕获具体异常。
2. 为重试设置次数与时间预算。
3. 保留原异常链和请求身份。
4. 对无法恢复的状态停止后续处理。

按这个顺序保留中间结果，可以区分输入条件、处理过程和最终输出。前一阶段的条件不成立时，先解释对应错误，再继续后面的试验；单次返回成功不足以覆盖整条链路。

### 最小示例

```python
try:
    result = parse_input(payload)
except ValueError as exc:
    raise ValueError("invalid input") from exc
```

parse_input 与 payload 是待实现业务的示意变量，片段不作为独立可运行程序。保留异常链可以定位原始原因，输入错误应与网络失败分开处理；需要重试的副作用先核对幂等。

示例聚焦当前技术关系。引用的图片、数据库、消息对象或处理函数，需要由调用环境提供；它不包含完整服务的认证、持久化与并发管理。验证时先用受控输入检查，再纳入应用。

## 四、验证和结果解释

记录解释器来源、必要版本和最小复现输入，再保存有效错误链。安装失败按下载、构建、链接与导入阶段分析，执行失败按输入、资源和结果归属分析。公开示例使用通用路径与虚构业务对象，不输出个人环境或原始附件。

| 需要验证的结果 | 保留的对照 | 不能由此推出的结论 |
| --- | --- | --- |
| 输入错误不会变成默认成功 | 固定输入与配置、对应输出 | 一次成功代表所有条件成功 |
| 重复失败能定位第一条原因 | 中断前后状态与错误阶段 | 没有报错代表结果正确 |
| 清理逻辑在成功和异常时都执行 | 恢复后的同条件复测 | 临时恢复代表根因已经消失 |

验证包括格式错误、资源不可用、任务取消与进程重启。并发提升要同时检查吞吐、尾延迟、内存与错误，不能只增加 worker 数量。文件发布、数据库提交和业务动作仍有各自原子性边界，需要分别确认。

## 五、适用边界与结论

不要对所有异常无限重试。重试涉及写入时先确认幂等，进程继续存活不表示业务已经完成。

这条路径把“按操作范围捕获具体异常”与“对无法恢复的状态停止后续处理”连在一起，中间保留可复查的条件。实施时优先确认“输入错误不会变成默认成功”，再检查“清理逻辑在成功和异常时都执行”；两者都满足，才能在当前样本与配置范围内评价方案。设备、数据或软件版本改变以后，相关假设需要重新验证。
