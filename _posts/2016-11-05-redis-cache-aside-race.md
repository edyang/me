Cache Aside（旁路缓存）常用数据库更新后删除缓存，但并发读写仍可能产生短暂陈旧值。

本文使用Redis 3.0 与 Java 应用，代码为协议命令或流程示意。缓存保存的是可重建视图还是关键状态，决定了失效和故障时的处理。本文先以数据库为权威来源，不把缓存命中等同于业务事实已经确认。

## 1. 从现象推到机制

读取方可能在删除前读到旧数据库值，却在删除后把它写回缓存。缓存与数据库不共享原子事务，因此需要根据可接受陈旧程度选择过期、版本或更可靠的失效机制。任何简单顺序都不应被写成绝对一致。

## 2. 最小实现与输入条件

用两个执行流程画出交错时序，明确哪一步读取了旧值。先定义业务允许的陈旧窗口，再决定是否需要版本比较。

```text
reader: miss -> read old database value -> delayed cache set
writer: update database -> delete cache
possible result: old value repopulated after deletion
```

在独立实例准备演示键，观察命中、过期和数据库回源次数。键包含必要的业务作用域，日志与指标避免记录完整敏感值，缓存故障路径也要能验证。

## 3. 用对照区分原因

下表列出需要主动改变的条件。预期行为来自机制分析，复现时还需记录运行环境和原始输出，不能将预期当作已经测得的结果。

| 改变的条件 | 需要验证的行为 |
| --- | --- |
| 读方延迟回填旧值 | 删除后仍可能再次出现旧缓存 |
| 设置有限过期时间 | 可限制部分陈旧持续时间 |
| 业务不允许陈旧结果 | 应使用更强依据或绕过该缓存 |

### 对照 1：读方延迟回填旧值

删除后仍可能再次出现旧缓存。观察时记录读库与回填的真实先后。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。
### 对照 2：设置有限过期时间

可限制部分陈旧持续时间。观察时记录过期配置与重建路径。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。
### 对照 3：业务不允许陈旧结果

应使用更强依据或绕过该缓存。观察时记录一致性需求与权威读取。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。

## 4. 适用条件与取舍

缓存问题需要结合失败重试分析。数据库更新成功而删除失败，应保留可恢复的失效任务，不能只把异常打印后忽略。

一次正常运行只覆盖了这组输入。继续扩展前，应把上面的异常对照保留下来，尤其关注“业务不允许陈旧结果”这一分支。后续方案若改变了图中任意一处依赖，原来的判断就要重新验证，不能仅凭界面相似或返回值相同沿用结论。
