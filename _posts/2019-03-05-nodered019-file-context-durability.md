启用持久上下文后，异常退出仍可能丢失最近变更。需要区分内存更新和文件刷新。

本文使用Node-RED 0.19、文件上下文存储与独立流程目录。流程可视化之后，还需要清楚的版本、状态和测试输入。编辑器画面不是完整交付，运行配置、凭据与安装节点版本也影响行为。

## 1. 从现象推到机制

0.19 引入外部上下文存储，默认仍可使用内存。文件存储可能通过缓存和周期刷新减少写盘，应用读取成功不必然证明数据已耐久保存。关键业务流水应使用明确事务语义的存储。

图中的四个节点分别表示上下文更新、存储实现、刷新时刻、恢复验证。顺着实线检查输入如何变成输出，再沿虚线核对反馈条件。图示表达的是本文讨论的关系，不是实测曲线或现场截图。

## 2. 最小实现与输入条件

在 settings.js 配置演示文件存储，正常重启与异常退出分别测试。不要把高频计数实验直接用于结算或不可丢事件。

```javascript
contextStorage: {
  default: { module: "localfilesystem" }
}
// 放入该版本 settings.js 的正确配置位置
// 核对实际刷新与关闭行为
```

先导出脱敏演示流程并记录依赖，使用固定消息回放。部署前核对变更范围，重启和异常退出分别验证；导出文件不能携带真实令牌或私人连接信息。

## 3. 用对照区分原因

下表列出需要主动改变的条件。预期行为来自机制分析，复现时还需记录运行环境和原始输出，不能将预期当作已经测得的结果。

| 改变的条件 | 需要验证的行为 |
| --- | --- |
| 正常重启后状态保留 | 只覆盖优雅关闭路径 |
| 修改后立即异常退出 | 最近缓存值未必已经刷新 |
| 所有状态都用文件上下文 | 可能混入不适合的关键数据 |

### 对照 1：正常重启后状态保留

只覆盖优雅关闭路径。观察时记录存储文件与重启读取值。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。
### 对照 2：修改后立即异常退出

最近缓存值未必已经刷新。观察时记录写入与文件刷新时刻。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。
### 对照 3：所有状态都用文件上下文

可能混入不适合的关键数据。观察时记录耐久性需求与存储语义。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。

## 4. 适用条件与取舍

持久化不是备份。目录损坏、磁盘故障和错误覆盖仍需独立恢复方案，流程版本与状态兼容也要检查。

一次正常运行只覆盖了这组输入。继续扩展前，应把上面的异常对照保留下来，尤其关注“所有状态都用文件上下文”这一分支。后续方案若改变了图中任意一处依赖，原来的判断就要重新验证，不能仅凭界面相似或返回值相同沿用结论。
