程序偶发退出、文件系统异常或板子重启，不一定是业务代码造成。电源和存储属于基础条件。

本文使用树莓派 3 Model B 与 Raspbian，使用独立测试存储卡。树莓派把 Linux 软件环境与实际供电、存储和接口连接起来。命令执行成功不证明电气连接正确，服务运行也不代表采集数据具有正确单位。

## 1. 从现象推到机制

外设瞬时负载、电源线压降与不稳定适配器都可能影响运行。存储卡写入异常和非正常断电也会产生问题。重启日志、欠压证据与应用错误需要放在一起比较，不能单靠一次现象认定原因。

图中的四个节点分别表示基础供电、系统状态、存储条件、应用结果。顺着实线检查输入如何变成输出，再沿虚线核对反馈条件。图示表达的是本文讨论的关系，不是实测曲线或现场截图。

## 2. 最小实现与输入条件

先减少到板子与必要外设，核对额定电源和线缆，再查看内核日志。使用独立测试卡验证镜像，不直接对唯一业务卡反复刷写。

```bash
dmesg | tail -n 80
vcgencmd get_throttled
df -h
# 按板型和系统文档解释状态位
```

记录板型、系统镜像和外设连接，先做单层验证再组合。操作使用有相应权限的普通账号，系统级调整才提升权限；不要把临时调试账户长期暴露在公共网络。

## 3. 用对照区分原因

下表列出需要主动改变的条件。预期行为来自机制分析，复现时还需记录运行环境和原始输出，不能将预期当作已经测得的结果。

| 改变的条件 | 需要验证的行为 |
| --- | --- |
| 增加 USB 外设后异常 | 需检查电源总预算和压降 |
| 存储空间耗尽 | 写入和服务可能失败 |
| 程序崩溃而系统未重启 | 应回到进程异常分析 |

### 对照 1：增加 USB 外设后异常

需检查电源总预算和压降。观察时记录连接变化与内核日志。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。
### 对照 2：存储空间耗尽

写入和服务可能失败。观察时记录文件系统空间与日志增长。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。
### 对照 3：程序崩溃而系统未重启

应回到进程异常分析。观察时记录系统启动时间与进程退出码。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。

## 4. 适用条件与取舍

一组欠压标记不是全部因果证据。还要确认状态含义、发生时刻和复现条件，修复后在相同负载下重新观察。

一次正常运行只覆盖了这组输入。继续扩展前，应把上面的异常对照保留下来，尤其关注“程序崩溃而系统未重启”这一分支。后续方案若改变了图中任意一处依赖，原来的判断就要重新验证，不能仅凭界面相似或返回值相同沿用结论。
