外部用户可访问公网入口，内网同一地址失败，不能只据此判断后端停止。回到本地目标的路径不同于真正外网访问。

回流 NAT 涉及目标转换与返回方向，响应绕过网关可能使会话不一致。分流 DNS 让内部域名解析到内部入口，减少回流依赖。

![内网访问公网入口：回流 NAT 与分流解析：处理路径与验证条件](/img/tech-notes/network-hairpin-nat.svg)

## 一、问题的范围与前提

单台 Linux 主机上的进程、文件、网络和服务管理有各自边界。排查时先确认当前命令所处的用户、网络命名空间与工作目录，再把进程状态和实际业务请求对应起来。交互终端、系统服务和容器可能同时使用不同环境，即使执行文件名称一样，也不代表访问同一组资源。

## 二、技术分析与方案取舍

诊断时直接内网入口成功，而相同域名公网地址失败，是区分回流路径的有用证据。抓取请求与响应方向，可以检查是否经过预期网关。分流解析减少绕行，但证书域名和前端来源仍保持一致；不能把内部地址随意替换成另一个服务实例。任何路由或 NAT 调整都先检查现有规则与拓扑，保留回退条件。

变更应围绕已经定位的条件进行。先保存当前有效配置与一段故障日志，再修改一个变量，使用同一入口复测。服务重启只重新执行当前单元，单元文本改变后还需按管理器规则重新加载；网络配置改变也可能影响已有连接。每一步都应能说明它解决的是地址、权限、环境还是进程生命周期。

## 三、实现与排查的顺序

1. 记录内外请求路径。
2. 核对返回方向。
3. 比较直接内网入口。
4. 按需求选择回流或分流。

按这个顺序保留中间结果，可以区分输入条件、处理过程和最终输出。前一阶段的条件不成立时，先解释对应错误，再继续后面的试验；单次返回成功不足以覆盖整条链路。

### 最小示例

```bash
ip -br link
ip -br address
ip route
ip neigh
```

链路、地址、路由与邻居表分别反映不同阶段。公开记录要泛化真实地址和硬件标识。对照故障前后的变化，再使用实际业务端口验证，不能让一次 ping 成功替代完整协议路径。

## 四、验证和结果解释

进程 PID、监听地址、错误发生时间与退出状态适合形成一组关联证据。单次截图通常不足以解释间歇故障，持续观察可以发现状态转换和重复失败间隔。公开记录只保留必要错误类型与通用路径，认证信息、真实主机名和内部地址不进入文章。

| 需要验证的结果 | 保留的对照 | 不能由此推出的结论 |
| --- | --- | --- |
| 请求响应经过一致路径 | 固定输入与配置、对应输出 | 一次成功代表所有条件成功 |
| 证书域名匹配 | 中断前后状态与错误阶段 | 没有报错代表结果正确 |
| 内外入口使用预期实例 | 恢复后的同条件复测 | 临时恢复代表根因已经消失 |

故障复现时要区分稳定错误和偶发错误。稳定错误优先检查固定配置，偶发错误再看资源峰值、连接状态和时间变化。修复后既测正常路径，也验证启动失败、依赖不可达与重启条件，避免只在已有运行环境中成功。

## 五、适用边界与结论

不能复制 NAT 规则到未知拓扑。多网卡、代理与桥接都可能改变返回路径。

这条路径把“记录内外请求路径”与“按需求选择回流或分流”连在一起，中间保留可复查的条件。实施时优先确认“请求响应经过一致路径”，再检查“内外入口使用预期实例”；两者都满足，才能在当前样本与配置范围内评价方案。设备、数据或软件版本改变以后，相关假设需要重新验证。
