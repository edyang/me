需求写成“做个订单列表”，开发和验收可能各自理解成不同东西。任务边界需要在动手之前具体化。

本文使用Java Web 小项目的演示工程与协作场景。初入团队时，重要的不只是写出功能，还包括让别人能够复现、审查和接手。本文使用匿名任务说明工作方法，不指代某家公司的内部流程或真实交付成绩。

## 1. 从现象推到机制

列表至少涉及谁能看、显示什么、怎样排序、如何筛选和空结果怎么表达。页面组件只是结果载体，数据权限和金额口径才决定内容是否正确。把加载失败与没有数据区分，也能减少后续误报。

图中的四个节点分别表示需求描述、条件清单、演示输入、验收反馈。顺着实线检查输入如何变成输出，再沿虚线核对反馈条件。图示表达的是本文讨论的关系，不是实测曲线或现场截图。

## 2. 最小实现与输入条件

先给每个条件写一个输入与预期结果，演示数据覆盖不同权限和状态。只做本轮确认的字段，不把未来可能需要的功能自动纳入。

```text
role: own_orders_only
columns: number, amount, status
sort: created_at DESC, id DESC
empty: explicit empty message
error: retry entry with no fake rows
```

示例命令需要在独立演示工程中执行，路径和服务均由读者准备。操作前保留当前版本与输入，修改后对照原来的问题验证，而不是只证明新代码能够编译。

## 3. 用对照区分原因

下表列出需要主动改变的条件。预期行为来自机制分析，复现时还需记录运行环境和原始输出，不能将预期当作已经测得的结果。

| 改变的条件 | 需要验证的行为 |
| --- | --- |
| 普通用户查询别人的订单 | 结果不得越过数据权限 |
| 相同创建时间有多条记录 | 翻页仍保持稳定顺序 |
| 接口返回错误 | 页面不能显示成没有订单 |

### 对照 1：普通用户查询别人的订单

结果不得越过数据权限。观察时记录服务端查询条件而非隐藏按钮。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。
### 对照 2：相同创建时间有多条记录

翻页仍保持稳定顺序。观察时记录排序是否含唯一的次级键。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。
### 对照 3：接口返回错误

页面不能显示成没有订单。观察时记录错误状态与空结果分支。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。

## 4. 适用条件与取舍

验收条件要以业务行为描述，避免绑定某个实现类。实现方式可以调整，只要权限、输入输出和约定体验保持可验证。

一次正常运行只覆盖了这组输入。继续扩展前，应把上面的异常对照保留下来，尤其关注“接口返回错误”这一分支。后续方案若改变了图中任意一处依赖，原来的判断就要重新验证，不能仅凭界面相似或返回值相同沿用结论。
