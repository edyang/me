项目能编译，运行却报找不到方法，可能是实际加载的 jar 与编译期版本不同。

本文使用Java Web 小项目的演示工程与协作场景。初入团队时，重要的不只是写出功能，还包括让别人能够复现、审查和接手。本文使用匿名任务说明工作方法，不指代某家公司的内部流程或真实交付成绩。

## 1. 从现象推到机制

传递依赖让一个库间接带入另一个库，冲突调解决定最终选用的版本。应用服务器自带库与 WAR 中的库还可能形成另一层覆盖。复制一个更新 jar 进去，通常只会让来源更难追踪。

图中的四个节点分别表示声明依赖、解析结果、打包产物、运行来源。顺着实线检查输入如何变成输出，再沿虚线核对反馈条件。图示表达的是本文讨论的关系，不是实测曲线或现场截图。

## 2. 最小实现与输入条件

先输出依赖树，再检查最终 WAR 包与运行时类来源。对确实需要统一的依赖使用明确版本管理，并保留排除某项传递依赖的原因。

```bash
mvn dependency:tree
mvn help:effective-pom
mvn package
jar tf target/demo.war
```

示例命令需要在独立演示工程中执行，路径和服务均由读者准备。操作前保留当前版本与输入，修改后对照原来的问题验证，而不是只证明新代码能够编译。

## 3. 用对照区分原因

下表列出需要主动改变的条件。预期行为来自机制分析，复现时还需记录运行环境和原始输出，不能将预期当作已经测得的结果。

| 改变的条件 | 需要验证的行为 |
| --- | --- |
| 依赖树存在多个候选版本 | 最终版本受解析规则影响 |
| WAR 中版本正确仍报错 | 继续检查服务器共享类库 |
| 开发机成功但干净环境失败 | 可能依赖本地手工安装包 |

### 对照 1：依赖树存在多个候选版本

最终版本受解析规则影响。观察时记录选中的依赖路径。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。
### 对照 2：WAR 中版本正确仍报错

继续检查服务器共享类库。观察时记录实际类加载来源。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。
### 对照 3：开发机成功但干净环境失败

可能依赖本地手工安装包。观察时记录仓库配置与构建输入。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。

## 4. 适用条件与取舍

清理本地仓库不是所有依赖问题的答案。先固定坐标和来源，才能判断是下载损坏、版本冲突还是部署内容没更新。

一次正常运行只覆盖了这组输入。继续扩展前，应把上面的异常对照保留下来，尤其关注“开发机成功但干净环境失败”这一分支。后续方案若改变了图中任意一处依赖，原来的判断就要重新验证，不能仅凭界面相似或返回值相同沿用结论。
