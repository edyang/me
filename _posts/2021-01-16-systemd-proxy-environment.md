同一命令在交互终端成功，服务执行却失败，应先比较运行环境。终端继承的代理、PATH 和工作目录不会自动成为系统服务配置。

服务用户、环境和文件权限构成独立上下文。HTTP 代理、DNS、证书与目标协议分别影响访问，浏览器成功不能替代服务进程测试。

![systemd 网络配置：终端可访问而后台服务失败：处理路径与验证条件](/img/tech-notes/systemd-proxy-environment.svg)

## 一、问题的范围与前提

单台 Linux 主机上的进程、文件、网络和服务管理有各自边界。排查时先确认当前命令所处的用户、网络命名空间与工作目录，再把进程状态和实际业务请求对应起来。交互终端、系统服务和容器可能同时使用不同环境，即使执行文件名称一样，也不代表访问同一组资源。

## 二、技术分析与方案取舍

对照可以先从执行者开始：哪个用户启动，工作目录在哪里，调用的程序是否与终端相同。代理配置如果只放在交互 shell 初始化文件，系统服务未必读取；若代理需要认证，日志仅说明是否配置及连接阶段。目标服务 HTTPS 失败还需检查证书和时间，不因 HTTP 下载成功就结束排查。

复测使用同一个资源与方法，避免测试对象变化。 Arduino 等工具链下载还可能包含多个独立域名，包索引更新成功不代表编译器归档也能取得。GUI、交互终端和后台服务的代理环境分别核对，缓存文件先验证大小与解压，不把下载超时当作代码编译错误。

离线安装固定版本与校验来源，再从最小工程验证工具链。

变更应围绕已经定位的条件进行。先保存当前有效配置与一段故障日志，再修改一个变量，使用同一入口复测。服务重启只重新执行当前单元，单元文本改变后还需按管理器规则重新加载；网络配置改变也可能影响已有连接。每一步都应能说明它解决的是地址、权限、环境还是进程生命周期。

## 三、实现与排查的顺序

1. 记录服务用户和执行路径。
2. 显式配置必要环境变量。
3. 在服务上下文访问目标。
4. 对照代理连接与目标响应。

按这个顺序保留中间结果，可以区分输入条件、处理过程和最终输出。前一阶段的条件不成立时，先解释对应错误，再继续后面的试验；单次返回成功不足以覆盖整条链路。

### 最小示例

```bash
systemctl show example.service -p User -p WorkingDirectory
systemctl show example.service -p ExecStart
journalctl -u example.service --since "15 minutes ago"
```

这些只读查询用于对照服务上下文和日志。环境可能包含敏感项，不应无差别导出并公开；查看代理配置时只记录变量是否设置与连接结果。运行用户和路径正确以后，再核对目标协议、证书和网络。

## 四、验证和结果解释

进程 PID、监听地址、错误发生时间与退出状态适合形成一组关联证据。单次截图通常不足以解释间歇故障，持续观察可以发现状态转换和重复失败间隔。公开记录只保留必要错误类型与通用路径，认证信息、真实主机名和内部地址不进入文章。

| 需要验证的结果 | 保留的对照 | 不能由此推出的结论 |
| --- | --- | --- |
| 重启后配置仍生效 | 固定输入与配置、对应输出 | 一次成功代表所有条件成功 |
| 代理与目标失败可区分 | 中断前后状态与错误阶段 | 没有报错代表结果正确 |
| 日志不输出认证信息 | 恢复后的同条件复测 | 临时恢复代表根因已经消失 |

故障复现时要区分稳定错误和偶发错误。稳定错误优先检查固定配置，偶发错误再看资源峰值、连接状态和时间变化。修复后既测正常路径，也验证启动失败、依赖不可达与重启条件，避免只在已有运行环境中成功。

## 五、适用边界与结论

环境文件应限制权限。需要代理的是实际发起请求的进程，不能只修改当前 shell。

这条路径把“记录服务用户和执行路径”与“对照代理连接与目标响应”连在一起，中间保留可复查的条件。实施时优先确认“重启后配置仍生效”，再检查“日志不输出认证信息”；两者都满足，才能在当前样本与配置范围内评价方案。设备、数据或软件版本改变以后，相关假设需要重新验证。
