同账号不同入口结果不同，先检查是否到同一后端与账号库。

统一错误文案可能掩盖网络、代理和服务异常。localhost、缓存、API基址和会话存储在不同终端含义不同。

![办公室登录正常而现场失败：请求入口对照：处理路径与验证条件](/img/tech-notes/same-account-office-tablet-login-failure.svg)

## 一、问题的范围与前提

浏览器所看到的页面、实际请求地址与服务器收到的路径要对应起来。页面来源、代理、缓存、Cookie 和连接生命周期分别影响行为。桌面浏览器、平板与嵌入式 WebView 可能具有不同访问条件，不能把某一端成功直接视为所有终端都已通过。

## 二、技术分析与方案取舍

先比较办公室与平板实际请求的协议、主机、端口、路径和响应状态。办公室可能通过穿透入口访问，现场则走局域网地址，两端成功条件并不相同。若平板请求根本未到后端，继续查 DNS、路由、混合内容或 WebView 网络策略；若已经到达，核对代理路径、认证字段和 Cookie。

页面显示统一登录失败文案，可能覆盖网络异常或后端 5xx，不应立即重置密码。对照同一次请求的时间和后端记录，并在日志中隐藏凭据。修复后清理或更新缓存版本，再从现场入口实际验证。

实现时明确入口和 API 基址，页面或组件销毁后清理连接与定时器。版本更新需要考虑旧页面并存，错误提示保留网络、鉴权和依赖异常的区别。若采用代理，路径替换和协议头按预期上游核对，不能同时在多处随意拼接前缀。

## 三、实现与排查的顺序

1. 对照实际请求路径。
2. 排除旧页面缓存。
3. 关联后端状态。
4. 检查登录后会话。

按这个顺序保留中间结果，可以区分输入条件、处理过程和最终输出。前一阶段的条件不成立时，先解释对应错误，再继续后面的试验；单次返回成功不足以覆盖整条链路。

### 最小示例

```text
页面源 → 实际 API → 代理上游 → 后端结果
对照：方法、路径、状态码、时间
凭据：只记录是否存在，不输出实际内容
```

这组关系帮助区分网络、路由与身份认证。登录成功后的首条业务请求往往比统一错误文案更有用，缓存和终端生命周期也要放到同一时间链。

## 四、验证和结果解释

一组完整的排查资料应能展示请求方法、路径、响应状态与时间，以及相关后端记录。只展示一个登录失败截图，无法判断请求是否到达目标服务。共享记录时移除凭据和个人信息，仅保留非敏感字段、状态与必要结构。

| 需要验证的结果 | 保留的对照 | 不能由此推出的结论 |
| --- | --- | --- |
| 根因按响应区分 | 固定输入与配置、对应输出 | 一次成功代表所有条件成功 |
| 无凭据泄露 | 中断前后状态与错误阶段 | 没有报错代表结果正确 |
| 不同入口连接预期实例 | 恢复后的同条件复测 | 临时恢复代表根因已经消失 |

验证应覆盖首次打开、缓存命中、刷新、断网恢复与后台切换。连接状态和最后有效数据分别显示，旧数据不能因页面仍打开而永久看作实时。发布后的页面和静态资源还应逐项核对，不仅检查仓库文件是否存在。

## 五、适用边界与结论

没有现场日志时不认定密码或网络为唯一原因。

这条路径把“对照实际请求路径”与“检查登录后会话”连在一起，中间保留可复查的条件。实施时优先确认“根因按响应区分”，再检查“不同入口连接预期实例”；两者都满足，才能在当前样本与配置范围内评价方案。设备、数据或软件版本改变以后，相关假设需要重新验证。
