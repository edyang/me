同一个收入数字在汇报、合同表和银行流水中口径不同，会使经营判断失去基础。

本文使用虚构经营数据与简单股权、现金流模型。经营模型先服务于识别假设和约束。文中没有真实融资交易、客户财务或收益承诺；比例与金额只是演算输入，实际条款仍需专业人员结合完整材料确认。

## 1. 从现象推到机制

资料包应区分合同额、确认收入、开票与回款，分别标注期间和来源。业务预测与已实现数据不能混排。技术资产也需要区分自研、开源依赖和第三方授权，不能把能运行的演示一概称为自有知识产权。

## 2. 最小实现与输入条件

先建立索引页，只向需要的角色开放必要资料。公开交流使用匿名汇总，原合同和个人信息保留在受控位置。

```text
metric -> definition -> period -> source
forecast -> assumptions -> sensitivity
software -> ownership -> dependency -> license
access -> reviewer_role -> permitted_scope
```

把原始数据、假设和推导结果分别保存，明确时间范围与单位。至少改变一个关键变量做敏感性比较，不因单一乐观情景看起来可行，就把预测当作已经实现的结果。

## 3. 用对照区分原因

下表列出需要主动改变的条件。预期行为来自机制分析，复现时还需记录运行环境和原始输出，不能将预期当作已经测得的结果。

| 改变的条件 | 需要验证的行为 |
| --- | --- |
| 合同额高而回款很少 | 需要单独解释收款和履约条件 |
| 预测混入已实现数据 | 应拆开标示不同确定性 |
| 演示含第三方组件 | 要核对授权而非声称全部自研 |

### 对照 1：合同额高而回款很少

需要单独解释收款和履约条件。观察时记录合同与现金各自来源。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。
### 对照 2：预测混入已实现数据

应拆开标示不同确定性。观察时记录事实截止点和预测假设。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。
### 对照 3：演示含第三方组件

要核对授权而非声称全部自研。观察时记录组件来源与使用许可。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。

## 4. 适用条件与取舍

资料完整不保证融资成功，但能提高讨论可核对性。披露范围要与交易阶段匹配，不能为追求完整随意公开敏感材料。

一次正常运行只覆盖了这组输入。继续扩展前，应把上面的异常对照保留下来，尤其关注“演示含第三方组件”这一分支。后续方案若改变了图中任意一处依赖，原来的判断就要重新验证，不能仅凭界面相似或返回值相同沿用结论。
