代码回退了，服务行为却没有恢复，原因可能是镜像、依赖或数据库状态没有一起回退。交付版本应描述真正运行的组合，而不是只记一个分支名字。

提交标识代表源码快照，镜像摘要代表构建结果，配置版本代表运行条件，数据迁移则改变持久状态。它们之间需要关联，才能判断一个版本是否可再次部署。

![Git 管理部署版本：代码、配置与镜像一起追踪：处理路径与验证条件](/img/tech-notes/git-deployment-version.svg)

## 一、问题的范围与前提

技术交付包含环境、接口、数据、权限和验证范围。某个模块演示成功，不代表整套系统已验收。应将已有结果、工程目标和待验证条件分别记录，让读者知道结论能够应用到哪里。

## 二、技术分析与方案取舍

发布标记可以关联源码提交、依赖清单、镜像摘要、配置模板和迁移版本。镜像标签可读但可能被重新推送，因此严格复现还需要摘要。回退前核对旧程序是否兼容新数据，特别是字段删除、单位变换和状态枚举改版。配置模板只说明变量和用途，真实凭据由运行环境管理。

维护者应能从当前服务标识回到这组产物，而不是凭目录名称猜版本。

从业务动作和现场约束建立任务边界，再确定各模块输入输出与责任。文档保存可重现的配置方法和异常路径，实际凭据独立管理。公开案例只分享已有资料能支持的过程，客户身份、内部数据、商业金额与未公开实现细节继续脱敏。

## 三、实现与排查的顺序

1. 记录源码提交与依赖清单。
2. 保存构建镜像标识。
3. 给环境配置建立受控版本。
4. 把迁移和回退条件加入发布记录。

按这个顺序保留中间结果，可以区分输入条件、处理过程和最终输出。前一阶段的条件不成立时，先解释对应错误，再继续后面的试验；单次返回成功不足以覆盖整条链路。

### 最小示例

```bash
git status --short
git log -5 --oneline
git rev-parse HEAD
git diff --stat
```

提交标识只说明源码状态，工作区可能还有未提交变化。部署记录还应关联镜像摘要、配置与迁移版本。这里不自动提交或回退，也不把含凭据的配置纳入版本管理。

## 四、验证和结果解释

每项结论有对应的样本、日志或验收条件，不以篇幅和图表数量替代证据。系统整体收益与单模块效果使用不同口径，重复建设内容不能多次归因。版本记录关联源码、配置和数据迁移，便于后续排查和恢复。

| 需要验证的结果 | 保留的对照 | 不能由此推出的结论 |
| --- | --- | --- |
| 同版本在独立环境可重建 | 固定输入与配置、对应输出 | 一次成功代表所有条件成功 |
| 回退后程序与数据相容 | 中断前后状态与错误阶段 | 没有报错代表结果正确 |
| 现场运行标识能追溯到源码 | 恢复后的同条件复测 | 临时恢复代表根因已经消失 |

验证需要由维护者在独立条件下复现，包括断网、重启、异常输入和回退。交付文件存在不代表部署完成，部署完成也不代表全部业务可用。限制应写成具体条件和检查方法，让下一次实施能够据此调整。

## 五、适用边界与结论

仓库不保存密码和私钥；配置模板只说明变量与用途。回到旧提交不意味着可以无条件回滚已迁移的数据。

这条路径把“记录源码提交与依赖清单”与“把迁移和回退条件加入发布记录”连在一起，中间保留可复查的条件。实施时优先确认“同版本在独立环境可重建”，再检查“现场运行标识能追溯到源码”；两者都满足，才能在当前样本与配置范围内评价方案。设备、数据或软件版本改变以后，相关假设需要重新验证。
