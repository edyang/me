同一个错误分散在多个服务中，没有共同请求身份就难以还原链路。

日志描述事件，指标描述分布，链路记录关联阶段。请求与业务身份可跨服务传播，但敏感内容和高基数字段需控制。

![部署可观察性：日志、指标与请求身份：处理路径与验证条件](/img/tech-notes/deployment-observation-chain.svg)

## 一、问题的范围与前提

接口由请求身份、参数语义、授权条件和结果状态共同构成。HTTP 层成功只描述传输与响应，业务处理还可能处于受理、执行或等待确认阶段。将外部输入转换为内部对象以后，仍需核对类型、范围和当前状态，不能因为 JSON 能解析就直接使用。

## 二、技术分析与方案取舍

同一请求 ID 从入口传到依赖日志，有助于定位首个失败阶段；业务事件 ID 则关联长期对象，两者不能混用。指标使用稳定标签维度，避免每个用户或任务都成为高基数序列。日志只保留必要结构和错误，不输出凭据和完整私有输入。回放一次失败即可检查链路是否真的可解释。

应用入口应有明确大小、时间和并发预算。正常和异常返回都遵循稳定结构，调用方可以据此选择等待、查询、修正或重试。涉及写入与外部动作时，为同一业务意图提供稳定身份，并在持久化边界内管理已受理结果，防止回执丢失造成重复执行。

## 三、实现与排查的顺序

1. 统一请求身份。
2. 定义关键阶段日志。
3. 采集延迟错误队列。
4. 按一次失败回放。

按这个顺序保留中间结果，可以区分输入条件、处理过程和最终输出。前一阶段的条件不成立时，先解释对应错误，再继续后面的试验；单次返回成功不足以覆盖整条链路。

### 最小示例

```text
对象 ID → 原始证据 → 派生结果 → 处置记录
每次变化保存：操作者角色、原因、状态与版本
```

这里说明审计关系，不保存真实个人身份。结果修改不覆盖原始证据，系统整体收益与模块性能分别记录，完成条件要与实际业务一致。

## 四、验证和结果解释

至少关联请求到达、关键依赖调用和处理结果。日志记录标识与阶段即可，密码、Cookie、token 和原始敏感请求不应进入公共记录。排查时用同一入口比较请求与响应，再结合后端证据，避免页面统一错误文案掩盖具体原因。

| 需要验证的结果 | 保留的对照 | 不能由此推出的结论 |
| --- | --- | --- |
| 可找到首个失败阶段 | 固定输入与配置、对应输出 | 一次成功代表所有条件成功 |
| 指标口径不混淆 | 中断前后状态与错误阶段 | 没有报错代表结果正确 |
| 日志不泄露认证数据 | 恢复后的同条件复测 | 临时恢复代表根因已经消失 |

验收除了正常返回，还包括重复提交、格式错误、依赖超时与调用方取消。系统应能对未知结果查询或恢复，而不是把每个超时都当成未执行。恢复范围尽量匹配故障，防止一个依赖异常引发所有服务同时反复重启。

## 五、适用边界与结论

收集越多不代表越可解释，关键字段和保留范围先于大规模采集。

这条路径把“统一请求身份”与“按一次失败回放”连在一起，中间保留可复查的条件。实施时优先确认“可找到首个失败阶段”，再检查“日志不泄露认证数据”；两者都满足，才能在当前样本与配置范围内评价方案。设备、数据或软件版本改变以后，相关假设需要重新验证。
