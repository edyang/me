需要两个常驻账号时，配置空间和启动入口应明确分离。

Profile 保存独立登录和扩展，user-data-dir 让目录与启动过程更清楚。两进程不应共享同一运行目录，浏览器隔离不等于系统安全隔离。

![Mac 双账号浏览器：Profile 与独立数据目录：处理路径与验证条件](/img/tech-notes/mac-chrome-independent-profiles.svg)

## 一、问题的范围与前提

浏览器所看到的页面、实际请求地址与服务器收到的路径要对应起来。页面来源、代理、缓存、Cookie 和连接生命周期分别影响行为。桌面浏览器、平板与嵌入式 WebView 可能具有不同访问条件，不能把某一端成功直接视为所有终端都已通过。

## 二、技术分析与方案取舍

普通Profile适合账号和扩展分离，独立user-data-dir把目录与启动过程也区分。两入口用不同名称或主题，首次打开核对实际空间。迁移前关闭浏览器，再按需要同步或导出，不复制正在写的目录。脚本处理路径空格，Dock快捷入口只是启动便利，不提供操作系统级安全隔离。

实现时明确入口和 API 基址，页面或组件销毁后清理连接与定时器。版本更新需要考虑旧页面并存，错误提示保留网络、鉴权和依赖异常的区别。若采用代理，路径替换和协议头按预期上游核对，不能同时在多处随意拼接前缀。

## 三、实现与排查的顺序

1. 选择隔离范围。
2. 规划目录或 Profile。
3. 建立可识别启动入口。
4. 核验实际账号配置。

按这个顺序保留中间结果，可以区分输入条件、处理过程和最终输出。前一阶段的条件不成立时，先解释对应错误，再继续后面的试验；单次返回成功不足以覆盖整条链路。

### 最小示例

```text
页面源 → 实际 API → 代理上游 → 后端结果
对照：方法、路径、状态码、时间
凭据：只记录是否存在，不输出实际内容
```

这组关系帮助区分网络、路由与身份认证。登录成功后的首条业务请求往往比统一错误文案更有用，缓存和终端生命周期也要放到同一时间链。

## 四、验证和结果解释

一组完整的排查资料应能展示请求方法、路径、响应状态与时间，以及相关后端记录。只展示一个登录失败截图，无法判断请求是否到达目标服务。共享记录时移除凭据和个人信息，仅保留非敏感字段、状态与必要结构。

| 需要验证的结果 | 保留的对照 | 不能由此推出的结论 |
| --- | --- | --- |
| 入口不串空间 | 固定输入与配置、对应输出 | 一次成功代表所有条件成功 |
| 重启保持配置 | 中断前后状态与错误阶段 | 没有报错代表结果正确 |
| 迁移不复制运行中目录 | 恢复后的同条件复测 | 临时恢复代表根因已经消失 |

验证应覆盖首次打开、缓存命中、刷新、断网恢复与后台切换。连接状态和最后有效数据分别显示，旧数据不能因页面仍打开而永久看作实时。发布后的页面和静态资源还应逐项核对，不仅检查仓库文件是否存在。

## 五、适用边界与结论

同步与导出按已有资料需求决定，不公开账号和浏览记录。

这条路径把“选择隔离范围”与“核验实际账号配置”连在一起，中间保留可复查的条件。实施时优先确认“入口不串空间”，再检查“迁移不复制运行中目录”；两者都满足，才能在当前样本与配置范围内评价方案。设备、数据或软件版本改变以后，相关假设需要重新验证。
