应用重建以后出现空目录，并不一定是数据被删除，也可能是卷名或挂载目标改变。部署前应先把程序文件、运行配置、可重建缓存和必须保存的业务数据分开。

容器可写层随容器生命周期变化，命名卷独立保存数据，bind mount 则映射指定宿主机路径。挂载会遮蔽镜像中相同位置的内容；匿名卷、命名卷与目录映射也有不同的发现和管理方式。

![Docker 数据卷：容器删除后哪些数据还能保留：处理路径与验证条件](/img/tech-notes/docker-volume-lifecycle.svg)

## 一、问题的范围与前提

镜像、容器、网络和数据卷是不同对象。镜像定义运行产物，容器执行进程，网络决定可达关系，卷管理跨容器生命周期的数据。把它们分别列出来，有助于判断重建究竟改变了什么；单个容器显示 Up，只能说明相关入口进程仍然存在。

## 二、技术分析与方案取舍

常见误判是修改 Compose 项目名称以后创建了另一组资源。旧卷可能仍在，只是新容器接入新卷。另一个误判是把宿主机空目录挂载到镜像已有数据的位置，挂载后看不到原内容，于是以为镜像数据消失。检查时先列出真实 Mounts，比较源与目标，再确认应用写入的位置。

业务备份则独立于这些路径：即便容器重建验证通过，主机损坏和误删卷仍需另一份恢复来源。

先固定基础镜像、应用版本和必要配置，再检查最终容器的实际参数。Compose 文件只是期望描述，已经创建的容器可能仍带旧环境。涉及端口、设备和挂载等创建参数时，需要按差异重建；普通 restart 不会重新读入全部创建配置。重建前确认数据所在位置和现有卷身份。

## 三、实现与排查的顺序

1. 确定业务实际写入路径。
2. 检查容器 Mounts 与卷身份。
3. 固定项目名和持久目录。
4. 在备份条件下验证重建读取。

按这个顺序保留中间结果，可以区分输入条件、处理过程和最终输出。前一阶段的条件不成立时，先解释对应错误，再继续后面的试验；单次返回成功不足以覆盖整条链路。

### 最小示例

```bash
docker inspect example-web
docker volume ls
docker volume inspect example_data
```

容器名称与卷名是示意，应使用已确认对象。Mounts 可以核对源、目标和类型，卷检查确认真实身份。读取这些信息不会证明备份有效，还需在独立环境验证恢复后的内容。

## 四、验证和结果解释

可以将配置解析结果、容器实际状态和一次业务请求放在一起观察。配置有效说明语法和部分引用成立，镜像构建有效说明产物生成，真实请求才进一步说明依赖链可用。将这些结果分开记录，能避免一个阶段的成功遮住另一个阶段的失败。

| 需要验证的结果 | 保留的对照 | 不能由此推出的结论 |
| --- | --- | --- |
| 重建后仍读取同一组样本 | 固定输入与配置、对应输出 | 一次成功代表所有条件成功 |
| 换项目名时能识别新卷与旧卷 | 中断前后状态与错误阶段 | 没有报错代表结果正确 |
| 恢复环境能独立读取备份数据 | 恢复后的同条件复测 | 临时恢复代表根因已经消失 |

容器异常不一定需要重建整套服务。先定位受影响对象，再确认是否有状态需要保留。数据卷独立于容器并不等于有独立备份，健康检查也不等于自动重启。恢复策略需要与退出、网络失联、数据损坏等具体条件对应。

## 五、适用边界与结论

卷独立于容器不等于备份独立于主机。活跃数据库目录不能未经一致性处理直接复制并认作有效备份；涉及删除卷的操作应先确认数据归属。

这条路径把“确定业务实际写入路径”与“在备份条件下验证重建读取”连在一起，中间保留可复查的条件。实施时优先确认“重建后仍读取同一组样本”，再检查“恢复环境能独立读取备份数据”；两者都满足，才能在当前样本与配置范围内评价方案。设备、数据或软件版本改变以后，相关假设需要重新验证。
