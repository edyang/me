共享键鼠需要两端配置和图形会话，安装成功不等于开机自动连接。

服务端持有键鼠，客户端接收输入，名称和屏幕位置决定路由。Flatpak 源、系统权限与桌面自启动分别配置。

![Deskflow 跨设备键鼠：安装、权限与登录启动：处理路径与验证条件](/img/tech-notes/deskflow-flatpak-startup.svg)

## 一、问题的范围与前提

浏览器所看到的页面、实际请求地址与服务器收到的路径要对应起来。页面来源、代理、缓存、Cookie 和连接生命周期分别影响行为。桌面浏览器、平板与嵌入式 WebView 可能具有不同访问条件，不能把某一端成功直接视为所有终端都已通过。

## 二、技术分析与方案取舍

共享键鼠先完成手动两端联通，再配置图形会话中的自启动。服务端和客户端名称、屏幕相对位置决定输入路由，系统启动与用户登录又是两个时机。Flatpak 安装源、网络代理和应用权限分别核对；代理端口应来自实际环境，文章使用占位配置。

客户端只有桌面会话建立后才适合接收输入，不能用一个没有显示环境的系统服务替代。测试开机、重新登录、断网恢复和服务端晚启动，检查是否只保留一个实例。最终还需从桌面快捷入口验证，终端中能启动只是其中一部分。

实现时明确入口和 API 基址，页面或组件销毁后清理连接与定时器。版本更新需要考虑旧页面并存，错误提示保留网络、鉴权和依赖异常的区别。若采用代理，路径替换和协议头按预期上游核对，不能同时在多处随意拼接前缀。

## 三、实现与排查的顺序

1. 手动确认两端可连。
2. 核对输入权限。
3. 设置登录后启动。
4. 测试断网重启。

按这个顺序保留中间结果，可以区分输入条件、处理过程和最终输出。前一阶段的条件不成立时，先解释对应错误，再继续后面的试验；单次返回成功不足以覆盖整条链路。

### 最小示例

```bash
flatpak list --app
# 将实际安装的应用 ID 代入，不猜包名
APP_ID=org.deskflow.deskflow
flatpak info "$APP_ID"
flatpak run "$APP_ID"
```

示例假定通过 Flatpak 安装。先核对实际应用 ID，再手动启动；登录自启动沿用桌面会话机制，服务端与客户端参数按已安装版本确认。

## 四、验证和结果解释

一组完整的排查资料应能展示请求方法、路径、响应状态与时间，以及相关后端记录。只展示一个登录失败截图，无法判断请求是否到达目标服务。共享记录时移除凭据和个人信息，仅保留非敏感字段、状态与必要结构。

| 需要验证的结果 | 保留的对照 | 不能由此推出的结论 |
| --- | --- | --- |
| 不要求远程桌面 | 固定输入与配置、对应输出 | 一次成功代表所有条件成功 |
| 布局正确 | 中断前后状态与错误阶段 | 没有报错代表结果正确 |
| 恢复只有一个实例 | 恢复后的同条件复测 | 临时恢复代表根因已经消失 |

验证应覆盖首次打开、缓存命中、刷新、断网恢复与后台切换。连接状态和最后有效数据分别显示，旧数据不能因页面仍打开而永久看作实时。发布后的页面和静态资源还应逐项核对，不仅检查仓库文件是否存在。

## 五、适用边界与结论

无图形系统服务不能直接替代桌面会话，包与应用 ID按实际安装核对。

这条路径把“手动确认两端可连”与“测试断网重启”连在一起，中间保留可复查的条件。实施时优先确认“不要求远程桌面”，再检查“恢复只有一个实例”；两者都满足，才能在当前样本与配置范围内评价方案。设备、数据或软件版本改变以后，相关假设需要重新验证。
