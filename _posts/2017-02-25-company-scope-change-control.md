客户说“顺手加一个小功能”，实际可能改变接口、数据结构和验收路径。小改动需要先看影响。

本文使用虚构经营数据与简单股权、现金流模型。经营模型先服务于识别假设和约束。文中没有真实融资交易、客户财务或收益承诺；比例与金额只是演算输入，实际条款仍需专业人员结合完整材料确认。

## 1. 从现象推到机制

变更描述应包括触发场景、目标行为、范围外内容和依赖。评估不仅是编码时间，还包括设计、联调、历史数据兼容和复验。已确认基线提供比较对象，避免每次讨论都重定义原需求。

![公司经营笔记：需求变更要连到工期和验收的处理、反馈与观察关系](/img/tech-notes/company-scope-change-control.svg)

图中的四个节点分别表示已确认基线、变更请求、影响评估、确认版本。顺着实线检查输入如何变成输出，再沿虚线核对反馈条件。图示表达的是本文讨论的关系，不是实测曲线或现场截图。

## 2. 最小实现与输入条件

用一张变更单连接原需求、变化内容、工作量和验收条件。未经确认的建议保留为待评估，不自动进入承诺交付。

```text
baseline -> requested_delta
impact -> roles, dependencies, schedule, cost
acceptance -> concrete inputs and expected behavior
decision -> confirmed scope and version
```

把原始数据、假设和推导结果分别保存，明确时间范围与单位。至少改变一个关键变量做敏感性比较，不因单一乐观情景看起来可行，就把预测当作已经实现的结果。

## 3. 用对照区分原因

下表列出需要主动改变的条件。预期行为来自机制分析，复现时还需记录运行环境和原始输出，不能将预期当作已经测得的结果。

| 改变的条件 | 需要验证的行为 |
| --- | --- |
| 只改变字段显示名称 | 影响可能主要在展示与文档 |
| 新增跨系统写入 | 需要重新评估权限和失败恢复 |
| 口头讨论尚未确认 | 不能当成已承诺范围 |

### 对照 1：只改变字段显示名称

影响可能主要在展示与文档。观察时记录接口及历史数据是否也受影响。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。
### 对照 2：新增跨系统写入

需要重新评估权限和失败恢复。观察时记录外部依赖与事务边界。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。
### 对照 3：口头讨论尚未确认

不能当成已承诺范围。观察时记录最终决策与版本依据。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。

## 4. 适用条件与取舍

流程应与变更规模匹配，不能让简单修正陷入冗长审批。但影响外部承诺和核心数据时，确认依据必须清楚。

一次正常运行只覆盖了这组输入。继续扩展前，应把上面的异常对照保留下来，尤其关注“口头讨论尚未确认”这一分支。后续方案若改变了图中任意一处依赖，原来的判断就要重新验证，不能仅凭界面相似或返回值相同沿用结论。
