能看到 AP 而 configuring 停滞，需按认证和地址阶段分析，不直接换静态 IP。

802.1X 认证通过以后才进入相应数据访问条件。账户过期、证书、DHCP 和路由分别影响连接，静态地址不绕过认证。

![企业 Wi-Fi：认证、DHCP 与业务访问：处理路径与验证条件](/img/tech-notes/enterprise-wifi-peap-auth-failure.svg)

## 一、问题的范围与前提

单台 Linux 主机上的进程、文件、网络和服务管理有各自边界。排查时先确认当前命令所处的用户、网络命名空间与工作目录，再把进程状态和实际业务请求对应起来。交互终端、系统服务和容器可能同时使用不同环境，即使执行文件名称一样，也不代表访问同一组资源。

## 二、技术分析与方案取舍

企业无线接入依次经过射频关联、EAP 认证、地址分配与业务访问。PEAP 的外层与内层身份、证书信任和时间条件会影响认证，不能把 DHCP 没拿到地址都解释为密码错误。先看失败阶段，认证成功再查 VLAN、地址池和路由。日志只保留方式、阶段与错误类型，不发布账号或证书材料。

固定同一终端与同一接入点比较，避免漫游把条件改变。修复后测试重连和系统重启，不通过关闭证书验证长期掩盖根因。

变更应围绕已经定位的条件进行。先保存当前有效配置与一段故障日志，再修改一个变量，使用同一入口复测。服务重启只重新执行当前单元，单元文本改变后还需按管理器规则重新加载；网络配置改变也可能影响已有连接。每一步都应能说明它解决的是地址、权限、环境还是进程生命周期。

## 三、实现与排查的顺序

1. 读取认证阶段日志。
2. 核对账户证书策略。
3. 验证地址和默认路由。
4. 最后检查业务端口。

按这个顺序保留中间结果，可以区分输入条件、处理过程和最终输出。前一阶段的条件不成立时，先解释对应错误，再继续后面的试验；单次返回成功不足以覆盖整条链路。

### 最小示例

```bash
ip -br link
ip -br address
ip route
ip neigh
```

链路、地址、路由与邻居表分别反映不同阶段。公开记录要泛化真实地址和硬件标识。对照故障前后的变化，再使用实际业务端口验证，不能让一次 ping 成功替代完整协议路径。

## 四、验证和结果解释

进程 PID、监听地址、错误发生时间与退出状态适合形成一组关联证据。单次截图通常不足以解释间歇故障，持续观察可以发现状态转换和重复失败间隔。公开记录只保留必要错误类型与通用路径，认证信息、真实主机名和内部地址不进入文章。

| 需要验证的结果 | 保留的对照 | 不能由此推出的结论 |
| --- | --- | --- |
| 错误阶段明确 | 固定输入与配置、对应输出 | 一次成功代表所有条件成功 |
| 证书校验保留 | 中断前后状态与错误阶段 | 没有报错代表结果正确 |
| 恢复覆盖完整路径 | 恢复后的同条件复测 | 临时恢复代表根因已经消失 |

故障复现时要区分稳定错误和偶发错误。稳定错误优先检查固定配置，偶发错误再看资源峰值、连接状态和时间变化。修复后既测正常路径，也验证启动失败、依赖不可达与重启条件，避免只在已有运行环境中成功。

## 五、适用边界与结论

公开记录去除 SSID 身份地址，不能为了临时连通无差别关闭证书校验。

这条路径把“读取认证阶段日志”与“最后检查业务端口”连在一起，中间保留可复查的条件。实施时优先确认“错误阶段明确”，再检查“恢复覆盖完整路径”；两者都满足，才能在当前样本与配置范围内评价方案。设备、数据或软件版本改变以后，相关假设需要重新验证。
