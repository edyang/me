模型返回合法 JSON 也可能包含错误枚举、范围或对象。解析后还需要业务校验。

语法、schema 与业务约束分别验证。未知字段、缺失值和跨字段关系不能只靠字符串格式保证，工具调用也需绑定权限与状态。

![模型结构化输出：可解析不等于可执行：处理路径与验证条件](/img/tech-notes/llm-structured-output-validation.svg)

## 一、问题的范围与前提

模型负责语言或特征推断，检索提供候选材料，程序验证结构与权限，执行层管理实际动作。各部分成功条件应单独定义。生成流畅、JSON 合法和工具调用受理，都不足以独立证明事实正确或业务已经完成。

## 二、技术分析与方案取舍

例如 JSON 的 status 字段值合法，却引用了不存在的对象，仍需业务校验；数值类型正确，却超出设备允许范围，也不能执行。未知字段、缺失字段和跨字段关系分别返回可定位错误。模型修正有预算，不无限循环。执行层再检查权限与当前状态，schema 只证明结构满足约束，不证明事实和授权。

先选择一个明确任务，固定输入、模型和工具范围，完成小样本端到端验证，再扩展数据与并发。引用和计算使用可反查证据，外部内容不授予执行权限。资源、上下文与时间都有预算，失败状态能被查询和恢复，避免在结果未知时盲目重做。

## 三、实现与排查的顺序

1. 定义明确结构及允许枚举。
2. 验证类型和范围。
3. 检查对象和跨字段条件。
4. 失败返回可修正反馈。

按这个顺序保留中间结果，可以区分输入条件、处理过程和最终输出。前一阶段的条件不成立时，先解释对应错误，再继续后面的试验；单次返回成功不足以覆盖整条链路。

### 最小示例

```json
{"schema_version": 1, "event_id": "example-001", "status": "pending", "payload": {}}
```

JSON 只是结构示意，后续需验证枚举、类型、对象与权限。事件 ID 不包含客户身份，版本只表达协议；合法解析不能代替事实与业务校验。

## 四、验证和结果解释

评估集覆盖正常、困难与越权条件，保存事实错误、引用错误、格式错误和工具错误的区别。模型输出与业务结果分开测量，目标指标不能冒充实测。已有官方能力说明只能支持候选范围，最终质量仍取决于目标数据和环境。

| 需要验证的结果 | 保留的对照 | 不能由此推出的结论 |
| --- | --- | --- |
| 不合法参数不进入执行 | 固定输入与配置、对应输出 | 一次成功代表所有条件成功 |
| 模型重试仍受预算 | 中断前后状态与错误阶段 | 没有报错代表结果正确 |
| 输出能追溯到输入与版本 | 恢复后的同条件复测 | 临时恢复代表根因已经消失 |

验证材料缺失、错误检索、依赖中断、资源不足与操作取消。系统应收窄结论或明确失败，不能为了给出答案补造证据。模型版本与处理参数成对保存，变更后重跑固定问题集，防止更自然的表达掩盖任务能力退步。

## 五、适用边界与结论

schema 不能证明事实正确，自动修补也可能改变原意。高风险命令不能因为 JSON 合法就直接执行。

这条路径把“定义明确结构及允许枚举”与“失败返回可修正反馈”连在一起，中间保留可复查的条件。实施时优先确认“不合法参数不进入执行”，再检查“输出能追溯到输入与版本”；两者都满足，才能在当前样本与配置范围内评价方案。设备、数据或软件版本改变以后，相关假设需要重新验证。
