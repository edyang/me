同一个双重循环，内层边界不同，增长速度可能完全不同。复习复杂度时，先把输入规模和基本操作说清楚。

本文使用经典算法与关系数据库的纸面例题。复习时把概念放进一个可手算的小问题：先声明假设，再列状态变化，最后检查反例。题目中的边界条件往往比公式本身更容易失分。

## 1. 从现象推到机制

顺序执行的两段循环取较大增长阶，嵌套循环则需要求和。若内层从零走到外层下标，总次数是等差数列，不是凭代码里有几个 for 就下结论。忽略常数只服务于渐近比较，不表示常数在工程中无影响。

图中的四个节点分别表示输入规模、循环边界、次数求和、增长比较。顺着实线检查输入如何变成输出，再沿虚线核对反馈条件。图示表达的是本文讨论的关系，不是实测曲线或现场截图。

## 2. 最小实现与输入条件

把 n 分别设为十、百、千，只累计加法次数，不夹带打印和磁盘访问。下面的计数表达式可直接手算，适合核对三角形循环。

```text
count = 0
for i = 0 .. n-1:
    for j = 0 .. i:
        count += 1
# count = n * (n + 1) / 2
```

例题中的规模和耗时都是教学输入。先手算一遍，再用短程序核对；记录推导过程，避免只背住选项或最终数字。实际系统的性能不能直接从纸面复杂度推出。

## 3. 用对照区分原因

下表列出需要主动改变的条件。预期行为来自机制分析，复现时还需记录运行环境和原始输出，不能将预期当作已经测得的结果。

| 改变的条件 | 需要验证的行为 |
| --- | --- |
| 输入翻倍 | 次数比值逐渐接近四 |
| 改为顺序循环 | 增长阶变为线性 |
| 内层固定十次 | 嵌套形式仍可为线性 |

### 对照 1：输入翻倍

次数比值逐渐接近四。观察时记录两次计数与各自的输入规模。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。
### 对照 2：改为顺序循环

增长阶变为线性。观察时记录循环边界是否仍存在依赖。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。
### 对照 3：内层固定十次

嵌套形式仍可为线性。观察时记录常数上界没有随输入增加。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。

## 4. 适用条件与取舍

复杂度比较应在相同问题、相同输出要求下进行。排序后再查找的方案要计入排序成本，单次查询与重复查询的最优选择可能不同；不能只比较最后一步。

一次正常运行只覆盖了这组输入。继续扩展前，应把上面的异常对照保留下来，尤其关注“内层固定十次”这一分支。后续方案若改变了图中任意一处依赖，原来的判断就要重新验证，不能仅凭界面相似或返回值相同沿用结论。
