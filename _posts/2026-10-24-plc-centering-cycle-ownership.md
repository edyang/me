一个归中工位由上位机、主控 PLC 和执行 PLC 协同完成：上位机允许接收工件，工件到位后执行归中夹紧，视觉确认后转台旋转，最后由机械手取走。问题出现在取走途中：工件可能再次遮挡同一只到位传感器，引起额外一次夹紧，接着下一件真正放入时反而不动作。

这种现象容易被归结为“传感器抖动”，但取料路径上的遮挡可能是完整、真实的电平变化。即使换成无抖动传感器，它仍会发生。排查重点应从信号是否变化，转向这次变化属于哪个工作周期、当前是否允许使用它。

本文将设备与通信标记泛化，讨论的是逻辑诊断与设计方法。观察到的异常尚不足以唯一确定根因，也没有现场连续运行通过的证据；下面的状态划分和测试表是待验证方案，不是可以直接下载到设备的程序。

![归中周期中许可消费、动作确认与取料隔离的关系](/img/tech-notes/plc-centering-cycle-ownership.svg)

## 一、先把预期顺序写成协议语义

为了不依赖具体设备地址，用三个符号表示已有消息：ALLOW 表示允许接收新工件，CENTERED 表示归中条件已确认，INSPECT 表示进入旋转检测。符号只表达业务含义，不是通用 PLC 指令，也不规定实际通信帧。

预期顺序是 ALLOW 到达、工件放入、归中完成、发送 CENTERED、收到 INSPECT、旋转完成、机械手取料。主控负责周期顺序，执行 PLC 负责机构动作及反馈。两者的通信成功、动作受理与机械完成必须分别记录。

| 对象 | 能证明什么 | 不能代替什么 |
| --- | --- | --- |
| ALLOW 消息 | 上位机提出新周期请求 | 工位空闲、机构就绪 |
| 到位传感器 | 检测区域被遮挡 | 新工件身份、机械手已离开 |
| 执行端受理确认 | 请求进入执行逻辑 | 夹紧到位与定位稳定 |
| 归中完成反馈 | 已定义的机械完成条件成立 | 后续旋转或取料完成 |

现有通用握手问题可参考[PLC 与上位机握手](/tech/2020/07/11/plc-message-latch-handshake/)。这里进一步处理同一传感器在一个周期内承担多种含义的问题。

## 二、两条故障链为什么会表现成一个问题

第一条链是旧命令反复生效。如果接收寄存器在数个扫描周期内一直保存 ALLOW，程序每次扫描都根据“值等于 ALLOW”置位许可，那么归中启动时即使清除了许可，下一次扫描仍可能重新置位。清除内部位无法消除上游持续成立的条件。

第二条链是未来许可被提前消耗。上位机可能在上一件取走之前就发送下一件的 ALLOW。如果主控只有一个“允许夹紧”位，而没有 WAIT_PART、INSPECTING、UNLOADING 等阶段，取料产生的第二次到位边沿便可能抢走下一件许可。于是上一件多夹一次、下一件缺少许可，两种症状出自同一个归属错误。

还有第三个需要单独检查的条件：执行端是否把保持高电平的启动位当作连续启动条件。当一个动作完成回到待机，启动位仍然为真，就可能再启动一次。这与主控是否正确识别新消息是两个层面，不能只修其中一个。

这些链条是解释现象的候选假设。确认它们需要同一时间窗口内的消息接收、主控状态、许可变化、启动请求与执行端状态，不能只看某个时刻的一张梯形图截图。

## 三、上升沿只能发现变化，不能识别放料

R_TRIG 的基本职责是记录输入前值，在低到高变化时输出一次执行周期的脉冲。Beckhoff 与 Schneider Electric 的标准库说明都将它定义为边沿检测器。持续高电平只产生一次脉冲，但先低后高会再次触发。

因此，把普通触点改成上升沿，可能修复持续电平反复启动，却不能阻止取料时第二次真实遮挡。正确条件应同时包含“新边沿”和“允许接收新件的状态”。边沿是电气变化，状态为它赋予业务含义。

另一个细节是调用位置。将边沿检测器只放在某个条件分支中调用，会使内部前值不一定反映每次扫描的输入历史。设计时应在固定周期任务中连续采样，再由状态机判断是否消费脉冲。启动时输入已经为高的情况，还要核对具体 PLC 的初始化与保持变量行为，不能假定所有库实例都一致。

单纯增加防抖时间也不解决阶段归属。它可能过滤短毛刺，同时也延迟真实工件到位。应先确认输入滤波、扫描周期和最短有效遮挡时间，再决定时间过滤；不能用大延时掩盖取料阶段缺少隔离的问题。

## 四、用单周期所有权约束夹紧入口

可以将主控流程拆为 IDLE、WAIT_PART、CENTERING、INSPECTING、UNLOADING 和 FAULT。进入 WAIT_PART 需要当前周期被受理、工位空闲及约定的前置条件成立；只有该状态可以消费新的到位边沿。

从 WAIT_PART 转向 CENTERING 时，许可在主控的同一次状态转换中被消费。后续扫描即使仍读到同一条消息，也不能重新给这个周期发放许可。完成反馈必须属于本周期，再决定发送 CENTERED。进入 INSPECTING 或 UNLOADING 之后，到位信号可以继续用于诊断，但不能回流到夹紧入口。

UNLOADING 的退出尤其关键。仅看到到位传感器变低，不能证明机械手已经离开危险区域；应结合设备已有的取料完成、机构位置或工位可用反馈，定义恢复到 IDLE 的条件。如果这些反馈缺失，应先补齐可观察条件，不能由软件随意猜测。

以下是**结构伪代码**，不是 IEC 61131-3 可编译程序。前提是通信层已输出有身份的受理事件、输入层每周期提供边沿、执行层提供带周期身份的完成反馈；所有标识均需由实现者映射到设备程序。

```text
每次周期任务：
    更新传感器历史，得到 part_rise
    读取并锁存协议事件，保留 cycle_id
    若存在故障：进入 FAULT，按设备定义处理输出
    否则按当前 state 处理：
        IDLE：仅在空闲条件满足时受理一个新 cycle_id
              设置 state = WAIT_PART
        WAIT_PART：若 part_rise 且周期有效：
                       消费本周期许可
                       创建归中请求，设置 state = CENTERING
        CENTERING：若本周期归中完成且机构条件满足：
                       发布 CENTERED，进入等待检测许可阶段
        INSPECTING：等待本周期旋转完成，然后进入 UNLOADING
        UNLOADING：待取料完成、工位清空及机构条件满足后回到 IDLE
```

为保持篇幅，伪代码省略了等待检测许可、取消及超时子状态；实现中这些出口必须明确。超时进入故障或待人工核对状态，不应直接跳回可夹紧状态。

## 五、双 PLC 的请求和反馈怎样闭合

如果允许扩展通信，建议请求与反馈携带 cycle_id 和动作类型，执行端对同一个动作身份只受理一次。反馈区分 ACCEPTED、BUSY、DONE 与 FAULT。通信重发只重发同一身份，不能把每次重试都变成新动作。

如果只能使用离散位，可采用四阶段握手：主控置请求；执行端受理并置确认；主控看到确认后撤请求；执行端看到请求撤销后撤确认。它明确一次请求何时结束，但仍需单独保存动作完成与故障状态。双方重启后不能无条件续接旧高电平，必须有恢复协调逻辑。

动作完成比请求确认更晚。如果 CENTERED 被上位机当作启动下一环节的条件，就应在真正的归中完成条件成立后发送。若旧系统的消息语义实际是“已受理”，应增加完成消息或调整调用方约定，不能只改一端的代码含义。

还有一个容易遗漏的情况：执行端已经动作，完成反馈在途中丢失。主控超时重发时，执行端应返回原动作状态，而不是重新夹紧。单纯加入一个脉冲位，无法解决跨重启和丢包情况下的去重。

## 六、记录哪些证据，才能区分根因

建议在隔离动作输出的测试环境先建立事件追踪，记录主控扫描序号、接收事件身份、状态转换、传感器原值与边沿、许可消费、执行请求和完成反馈。记录时间用于诊断，不作为跨 PLC 的唯一排序依据；不同控制器时钟可能存在偏差，周期身份与请求确认关系更可靠。

| 测试输入 | 预期行为 | 失败时优先核对 |
| --- | --- | --- |
| ALLOW 保持多个扫描周期 | 只受理一次 | 接收值是否被当作新事件 |
| 取料途中再次遮挡 | 不产生新归中请求 | UNLOADING 是否仍能消费到位边沿 |
| 忙碌时提前收到下一周期 | 明确拒绝或独立排队，不覆盖当前周期 | 是否共用一个许可位 |
| 执行确认或完成反馈延迟 | 保持可诊断状态，不重复动作 | 重试身份及 DONE 锁存 |
| 上电时传感器为高 | 进入定义的初始化核对流程 | 输入历史与残留请求 |
| 清空后放入下一件 | 新许可只启动一次 | 上周期清理与重新布防条件 |

模型回放可以验证“一个周期最多受理一次夹紧”等逻辑不变量，但不能验证传感器位置、机构惯性、气压、夹持力或硬接线。接到真实设备前，还需要对应 PLC 编译检查、任务周期核对以及由设备负责人组织的受控调试。本文的普通流程状态机不能替代安全回路。

## 七、结论：许可必须属于周期，信号必须属于阶段

重复夹紧和下一件不夹紧，可能同时来自许可的重复发放或提前消费。上升沿解决电平变化的提取，周期身份解决请求归属，状态机解决当前阶段允许做什么，动作握手解决两台控制器如何确认受理和完成。四者承担不同职责。

当前能得到的结论是排查顺序与设计约束：先验证旧消息是否反复置位，再检查取料阶段能否消费下一件许可，最后核对执行端的启动和完成闭环。没有同步追踪记录与现场回归结果之前，不能声称某一处改动已经消除了故障。
