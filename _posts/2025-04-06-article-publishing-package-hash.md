多个渠道分别保存正文容易漏同步，应保留明确唯一源与真实投递状态。

稿件、页面、素材和平台回执属于不同对象。草稿、已受理、公开发布和核验完成不等价，重试需稳定内容身份。

![多入口内容发布：唯一正文与平台状态：处理路径与验证条件](/img/tech-notes/article-publishing-package-hash.svg)

## 一、问题的范围与前提

接口由请求身份、参数语义、授权条件和结果状态共同构成。HTTP 层成功只描述传输与响应，业务处理还可能处于受理、执行或等待确认阶段。将外部输入转换为内部对象以后，仍需核对类型、范围和当前状态，不能因为 JSON 能解析就直接使用。

## 二、技术分析与方案取舍

多入口发布可以保留一个标题、摘要、正文和素材源，平台适配只处理允许的格式差异。每个平台保存草稿、受理、公开发布、失败或结果未知等实际状态。接口超时后先查原请求，不重新生成另一份稿件盲目重投。标题长度按目标计数规则验证，包含前缀和标点；图像则在支持上传的渠道转为该渠道认可的素材。

官网发布成功不能自动标记其它平台成功。验收既核对共用正文版本，也核对各渠道的公开链接和素材可用性。

应用入口应有明确大小、时间和并发预算。正常和异常返回都遵循稳定结构，调用方可以据此选择等待、查询、修正或重试。涉及写入与外部动作时，为同一业务意图提供稳定身份，并在持久化边界内管理已受理结果，防止回执丢失造成重复执行。

## 三、实现与排查的顺序

1. 维护唯一内容源。
2. 构建和素材校验。
3. 分阶段保存回执。
4. 核验真实公开入口。

按这个顺序保留中间结果，可以区分输入条件、处理过程和最终输出。前一阶段的条件不成立时，先解释对应错误，再继续后面的试验；单次返回成功不足以覆盖整条链路。

### 最小示例

```json
{
  "content_id": "example-article",
  "revision": 1,
  "source_sha256": "<最后一次构建后的实际摘要>",
  "channels": {
    "website": {"status": "pending", "url": null},
    "other": {"status": "pending", "url": null}
  }
}
```

这是结构示例，摘要占位符必须替换为实际文件结果。每个渠道独立保存真实状态；受理后未知不能直接写成 published。

## 四、验证和结果解释

至少关联请求到达、关键依赖调用和处理结果。日志记录标识与阶段即可，密码、Cookie、token 和原始敏感请求不应进入公共记录。排查时用同一入口比较请求与响应，再结合后端证据，避免页面统一错误文案掩盖具体原因。

| 需要验证的结果 | 保留的对照 | 不能由此推出的结论 |
| --- | --- | --- |
| 标题素材正文对应 | 固定输入与配置、对应输出 | 一次成功代表所有条件成功 |
| 未知先查询 | 中断前后状态与错误阶段 | 没有报错代表结果正确 |
| 更新不重复发文 | 恢复后的同条件复测 | 临时恢复代表根因已经消失 |

验收除了正常返回，还包括重复提交、格式错误、依赖超时与调用方取消。系统应能对未知结果查询或恢复，而不是把每个超时都当成未执行。恢复范围尽量匹配故障，防止一个依赖异常引发所有服务同时反复重启。

## 五、适用边界与结论

不把有文件或有PR当已发布，平台权限缺失需如实记录。

这条路径把“维护唯一内容源”与“核验真实公开入口”连在一起，中间保留可复查的条件。实施时优先确认“标题素材正文对应”，再检查“更新不重复发文”；两者都满足，才能在当前样本与配置范围内评价方案。设备、数据或软件版本改变以后，相关假设需要重新验证。
