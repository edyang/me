修改配置文件以后应用仍使用旧地址，排查应确认最终生效值，而不是只比较仓库里的文本。启动参数、环境变量、Profile 与外置配置可能覆盖包内默认设置。

配置来源有优先顺序，激活的 Profile 还会选择不同文件。打包产物与运行目录中的配置不一定相同，容器创建时读取的环境也不会因编辑 .env 自动刷新。

![Spring Boot 配置加载：环境变量与配置文件谁生效：处理路径与验证条件](/img/tech-notes/spring-boot-config-precedence.svg)

## 一、问题的范围与前提

应用配置、依赖注入、连接池和事务共同决定运行结果。启动日志没有异常，不代表业务依赖都已就绪。外置配置与包内默认值可能不同，实际使用的连接、Profile 和运行入口应先被确认。

## 二、技术分析与方案取舍

建议把一项错误配置沿启动命令、环境变量、外部文件和包内文件逐层追踪。配置文本被修改，却没有重启或重建相应实例时，程序可能仍使用已加载值。激活 test Profile 也不能只看文件名，需要确认运行日志或受控诊断中真正选择了哪个配置。

对于密码等敏感项，只验证来源与是否存在，不将实际内容打印到日志。版本升级后再核对配置名称和覆盖规则。

将环境配置从业务代码中分离，约束线程、连接和请求时间预算。数据库连接要在明确作用域内归还，事务异常有清晰回滚规则。对外接口和后台任务分别管理状态，不能仅依赖一个方法返回值描述跨系统完成情况。

## 三、实现与排查的顺序

1. 记录启动方式和激活 Profile。
2. 追踪配置来源及覆盖顺序。
3. 只输出非敏感的关键配置。
4. 重建或重启后核对实际连接。

按这个顺序保留中间结果，可以区分输入条件、处理过程和最终输出。前一阶段的条件不成立时，先解释对应错误，再继续后面的试验；单次返回成功不足以覆盖整条链路。

### 最小示例

```yaml
spring:
  profiles:
    active: test
  datasource:
    url: ${EXAMPLE_DB_URL}
    username: ${EXAMPLE_DB_USER}
    password: ${EXAMPLE_DB_PASSWORD}
```

片段展示外部变量和 Profile 关系，不包含可用凭据。变量需由实际运行环境提供，配置来源与覆盖顺序按目标版本核对。公开排查只展示结构，管理端点的访问范围另行限制。

## 四、验证和结果解释

从实际请求关联池状态、SQL 和异常堆栈，先找首个有效失败，再检查后续连锁错误。配置调试只公开非敏感来源与结构，不无差别开放环境或管理端点。并发负载使用固定输入和数据规模，避免环境变化影响比较。

| 需要验证的结果 | 保留的对照 | 不能由此推出的结论 |
| --- | --- | --- |
| 不同环境选择预期数据源 | 固定输入与配置、对应输出 | 一次成功代表所有条件成功 |
| 默认值不会掩盖配置缺失 | 中断前后状态与错误阶段 | 没有报错代表结果正确 |
| 敏感项不会进入启动日志 | 恢复后的同条件复测 | 临时恢复代表根因已经消失 |

验证正常启动、依赖不可达、连接耗尽与异常回滚。增加池容量不能替代数据库治理，放大超时也可能增加积压。版本变化时配置和依赖一起核对，不能以旧框架文档解释所有新运行行为。

## 五、适用边界与结论

配置优先顺序以所用 Spring Boot 版本为准。不能为了调试无差别公开 Actuator 环境端点，也不能把测试配置打包进生产镜像。

这条路径把“记录启动方式和激活 Profile”与“重建或重启后核对实际连接”连在一起，中间保留可复查的条件。实施时优先确认“不同环境选择预期数据源”，再检查“敏感项不会进入启动日志”；两者都满足，才能在当前样本与配置范围内评价方案。设备、数据或软件版本改变以后，相关假设需要重新验证。
