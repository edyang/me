本机主导镜像和只增加有不同删除行为，界面应明确哪一端拥有权威。

镜像让目标跟随来源，目标修改是否覆盖、来源删除何时传播都需定义。仅新增不等于完整版本备份，冲突与中断需保存状态。

![文件同步方向：镜像与只增加的语义：处理路径与验证条件](/img/tech-notes/desktop-sync-direction.svg)

## 一、问题的范围与前提

解释器、依赖、进程与任务状态是不同层次。代码能在一个目录执行，不表示服务或另一个虚拟环境使用相同模块。文件路径、导入来源和并发对象生命周期需要明确，尤其在多进程、长时间运行与异常重试中。

## 二、技术分析与方案取舍

镜像模式明确来源端权威，目标新增、修改和删除怎样处理要写清楚。只增加不传播删除，但也不自动提供每个文件历史版本。扫描差异与实际传输之间文件可能变化，需要再次核验；任务状态保存后支持中断继续。第一次执行先核对目录范围，避免把错误目标当正常空目录覆盖。

输入解析和业务处理之间建立明确边界，失败不默默变成默认成功值。使用标准库管理文件、队列与异常时，核对具体版本行为。外部副作用具有稳定身份，资源在正常与异常出口都被回收；共享可变对象只在明确同步与归属条件下使用。

## 三、实现与排查的顺序

1. 定义权威端和模式。
2. 建立差异扫描。
3. 事务记录任务。
4. 测试删除与冲突。

按这个顺序保留中间结果，可以区分输入条件、处理过程和最终输出。前一阶段的条件不成立时，先解释对应错误，再继续后面的试验；单次返回成功不足以覆盖整条链路。

### 最小示例

```python
from pathlib import Path
import os

target = Path("example.json")
temporary = target.with_suffix(".tmp")
temporary.write_text("{}", encoding="utf-8")
os.replace(str(temporary), str(target))
```

这段展示同目录临时文件与替换，适合单写者的可见性说明。它没有实现多写者锁，也未保证断电持久性。实际应用还要校验序列化结果、处理唯一临时名并按需要同步文件和目录。

示例聚焦当前技术关系。引用的图片、数据库、消息对象或处理函数，需要由调用环境提供；它不包含完整服务的认证、持久化与并发管理。验证时先用受控输入检查，再纳入应用。

## 四、验证和结果解释

记录解释器来源、必要版本和最小复现输入，再保存有效错误链。安装失败按下载、构建、链接与导入阶段分析，执行失败按输入、资源和结果归属分析。公开示例使用通用路径与虚构业务对象，不输出个人环境或原始附件。

| 需要验证的结果 | 保留的对照 | 不能由此推出的结论 |
| --- | --- | --- |
| 不会反向覆盖来源 | 固定输入与配置、对应输出 | 一次成功代表所有条件成功 |
| 中断可继续 | 中断前后状态与错误阶段 | 没有报错代表结果正确 |
| 用户能理解删除范围 | 恢复后的同条件复测 | 临时恢复代表根因已经消失 |

验证包括格式错误、资源不可用、任务取消与进程重启。并发提升要同时检查吞吐、尾延迟、内存与错误，不能只增加 worker 数量。文件发布、数据库提交和业务动作仍有各自原子性边界，需要分别确认。

## 五、适用边界与结论

不能用同步替代独立备份，首次执行先验证范围和数据身份。

这条路径把“定义权威端和模式”与“测试删除与冲突”连在一起，中间保留可复查的条件。实施时优先确认“不会反向覆盖来源”，再检查“用户能理解删除范围”；两者都满足，才能在当前样本与配置范围内评价方案。设备、数据或软件版本改变以后，相关假设需要重新验证。
