学习框架很容易停留在能运行示例。真正形成能力，需要把需求、实现、部署和反馈连接起来。

本文使用移动产品的假设案例与手工经营模型。这里讨论产品验证方法，不叙述未经记录的创业成绩。用户、订单和费用均为演算变量；商业假设需要访谈、行为数据与真实交易分别支持。

## 1. 从现象推到机制

选择一个窄场景，把用户任务写成可观察的结果。技术选型围绕当前约束，不把架构名词当作目标。每次迭代至少要回答一个真实问题，并保留失败路径；否则模块越来越多，仍不知道系统是否有用。

图中的四个节点分别表示任务定义、实现闭环、版本交付、反馈复盘。顺着实线检查输入如何变成输出，再沿虚线核对反馈条件。图示表达的是本文讨论的关系，不是实测曲线或现场截图。

## 2. 最小实现与输入条件

以小型预约工具为例：先完成提交、确认、取消，再加统计。每个功能注明触发条件、状态变化和用户能看到的反馈。

```text
task -> acceptance condition
implementation -> versioned source
deployment -> reachable service
feedback -> next concrete question
```

先把计算过程放入一张普通表格，保留原始分母、时间范围和渠道。改变一个变量观察结果，再用实际采样替换假设值；没有观测数据的地方应保持待验证。

## 3. 用对照区分原因

下表列出需要主动改变的条件。预期行为来自机制分析，复现时还需记录运行环境和原始输出，不能将预期当作已经测得的结果。

| 改变的条件 | 需要验证的行为 |
| --- | --- |
| 本地示例能运行 | 还不能说明用户能完成任务 |
| 发布后无法定位错误 | 需要补齐日志与版本标识 |
| 功能被持续使用 | 再收集具体困难决定下一步 |

### 对照 1：本地示例能运行

还不能说明用户能完成任务。观察时记录真实使用入口与任务结果。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。
### 对照 2：发布后无法定位错误

需要补齐日志与版本标识。观察时记录问题发生时对应的程序版本。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。
### 对照 3：功能被持续使用

再收集具体困难决定下一步。观察时记录行为记录与用户反馈。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。

## 4. 适用条件与取舍

学习计划不必覆盖所有热门技术。优先把当前最关键的一条链路走通，再根据明确瓶颈扩展，避免把不断重写当作进步。

一次正常运行只覆盖了这组输入。继续扩展前，应把上面的异常对照保留下来，尤其关注“功能被持续使用”这一分支。后续方案若改变了图中任意一处依赖，原来的判断就要重新验证，不能仅凭界面相似或返回值相同沿用结论。
