相同包名和类名的对象，仍可能无法互相转换。排查插件和应用服务器问题时，要把类加载器纳入身份判断。

本文使用JDK 7，示例为方法体或类定义片段。源码学习需要区分语言规则、公共接口约定与某个版本的实现。本文把讨论范围固定在 Java 7，不把后续版本的集合结构或语法写进来。

## 1. 从现象推到机制

运行时的类身份由二进制名称与定义它的类加载器共同确定。双亲委派通常先向父加载器请求，有助于共享基础类型，但自定义加载器可能采用不同策略。重复放置接口包会让插件与主程序各自加载一份接口。

## 2. 最小实现与输入条件

分别打印对象类与接口类的加载器，检查依赖包是否重复。先确认类从哪个路径加载，再考虑清理缓存或修改委派策略。

```java
System.out.println(obj.getClass().getName());
System.out.println(obj.getClass().getClassLoader());
System.out.println(Service.class.getClassLoader());
```

将片段放入独立的小工程，补齐 imports（导入声明）和调用入口。观察返回值、异常类型及对象状态；并发实验需要重复交错，单次没有出错不能证明线程安全。

## 3. 用对照区分原因

下表列出需要主动改变的条件。预期行为来自机制分析，复现时还需记录运行环境和原始输出，不能将预期当作已经测得的结果。

| 改变的条件 | 需要验证的行为 |
| --- | --- |
| 接口只由父加载器提供 | 主程序与插件可以共享接口身份 |
| 插件自带重复接口包 | 相同名称也可能不能强转 |
| 父加载器找不到目标类 | 子加载器才尝试自身定义 |

### 对照 1：接口只由父加载器提供

主程序与插件可以共享接口身份。观察时记录接口定义来自哪个加载器。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。
### 对照 2：插件自带重复接口包

相同名称也可能不能强转。观察时记录双方类加载器与代码来源。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。
### 对照 3：父加载器找不到目标类

子加载器才尝试自身定义。观察时记录委派与定义步骤的先后。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。

## 4. 适用条件与取舍

双亲委派是常见设计而不是任意加载器都必须遵守的万能规则。框架使用线程上下文加载器时，还要检查调用线程的上下文。
