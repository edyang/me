一个环境监测演示要真正闭环，需要从采样一路追到趋势与异常恢复，而不只是让看板有数字。

本文使用树莓派网关、独立视觉工作进程与合成业务事件。物联网与视觉结合后，数据采集、推理和业务动作有不同速率与可靠性。本文以可停止的演示链路研究状态归属，不把接口成功等同于物理动作完成。

## 1. 从现象推到机制

设备生成带单位、质量和身份的样本，网关保留原始采样时间并限速补传，服务端去重入库。趋势展示历史事实，告警只按新鲜有效数据判断。设备离线、采样失败和越限分别表达。

![物联网小系统：把采样、上报、趋势和告警串起来的处理、反馈与观察关系](/img/tech-notes/iot-environment-monitoring-demo.svg)

图中的四个节点分别表示采样契约、网关恢复、服务存储、趋势告警。顺着实线检查输入如何变成输出，再沿虚线核对反馈条件。图示表达的是本文讨论的关系，不是实测曲线或现场截图。

## 2. 最小实现与输入条件

先用合成数据代替传感器，再接额定范围内的台架传感器。故障按断网、重复、乱序与重启逐项加入，不报告未经实际完成的部署结果。

```text
sample -> id, value, unit, quality, sampled_at
gateway -> bounded durable pending queue
server -> dedup and store
trend -> historical samples
alert -> fresh valid samples and state machine
```

从单设备单图片开始，保存事件身份和所有输入输出。再逐项加入队列、重试和告警，检查重启后的归属与恢复；外部写入或控制需要明确规则与权限。

## 3. 用对照区分原因

下表列出需要主动改变的条件。预期行为来自机制分析，复现时还需记录运行环境和原始输出，不能将预期当作已经测得的结果。

| 改变的条件 | 需要验证的行为 |
| --- | --- |
| 重复补传同一样本 | 数据库与趋势只保留一次业务事实 |
| 设备在线但采样失败 | 显示数据质量异常 |
| 历史数据恢复上报 | 趋势可补齐但实时告警另按规则 |

### 对照 1：重复补传同一样本

数据库与趋势只保留一次业务事实。观察时记录样本唯一键。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。
### 对照 2：设备在线但采样失败

显示数据质量异常。观察时记录连接和采样状态分别记录。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。
### 对照 3：历史数据恢复上报

趋势可补齐但实时告警另按规则。观察时记录采样时刻与处理模式。把这个条件与基准情形分开，有助于判断变化来自哪一层；若得到相反结果，应先核对前提，再修改实现。

## 4. 适用条件与取舍

这是一套小系统的设计与验证路线。真实测量精度、可用性和告警效果，需要具体硬件、环境与持续记录支持。

一次正常运行只覆盖了这组输入。继续扩展前，应把上面的异常对照保留下来，尤其关注“历史数据恢复上报”这一分支。后续方案若改变了图中任意一处依赖，原来的判断就要重新验证，不能仅凭界面相似或返回值相同沿用结论。
