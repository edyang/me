配置静态地址后反复掉线，应分开检查链路、地址冲突与路由，而不是只改 DNS。

网卡连接、ARP 邻居、默认路由和业务端口各有状态。多个接口配置网关可能改变出口，地址冲突也可能表现为间歇可达。

![静态 IP 多网卡：默认路由与地址冲突：处理路径与验证条件](/img/tech-notes/network-static-ip-dual-route.svg)

## 一、问题的范围与前提

单台 Linux 主机上的进程、文件、网络和服务管理有各自边界。排查时先确认当前命令所处的用户、网络命名空间与工作目录，再把进程状态和实际业务请求对应起来。交互终端、系统服务和容器可能同时使用不同环境，即使执行文件名称一样，也不代表访问同一组资源。

## 二、技术分析与方案取舍

故障时先看网卡是否真正失去 carrier，再看地址是否保留和邻居是否变化。链路掉线与路由选择错误有不同证据。多接口各自配置默认网关时，出口优先级可能改变，内外目标还可能走不同路径。持续测试实际端口并对照内核日志，拔插恢复只是现象，不直接证明某项静态地址配置错误。

变更应围绕已经定位的条件进行。先保存当前有效配置与一段故障日志，再修改一个变量，使用同一入口复测。服务重启只重新执行当前单元，单元文本改变后还需按管理器规则重新加载；网络配置改变也可能影响已有连接。每一步都应能说明它解决的是地址、权限、环境还是进程生命周期。

## 三、实现与排查的顺序

1. 记录链路与内核事件。
2. 核对地址规划。
3. 检查路由优先级。
4. 持续测实际业务路径。

按这个顺序保留中间结果，可以区分输入条件、处理过程和最终输出。前一阶段的条件不成立时，先解释对应错误，再继续后面的试验；单次返回成功不足以覆盖整条链路。

### 最小示例

```bash
ip -br link
ip -br address
ip route
ip neigh
```

链路、地址、路由与邻居表分别反映不同阶段。公开记录要泛化真实地址和硬件标识。对照故障前后的变化，再使用实际业务端口验证，不能让一次 ping 成功替代完整协议路径。

## 四、验证和结果解释

进程 PID、监听地址、错误发生时间与退出状态适合形成一组关联证据。单次截图通常不足以解释间歇故障，持续观察可以发现状态转换和重复失败间隔。公开记录只保留必要错误类型与通用路径，认证信息、真实主机名和内部地址不进入文章。

| 需要验证的结果 | 保留的对照 | 不能由此推出的结论 |
| --- | --- | --- |
| 拔插前后变化可解释 | 固定输入与配置、对应输出 | 一次成功代表所有条件成功 |
| 出口符合规划 | 中断前后状态与错误阶段 | 没有报错代表结果正确 |
| 无重复地址与网关冲突 | 恢复后的同条件复测 | 临时恢复代表根因已经消失 |

故障复现时要区分稳定错误和偶发错误。稳定错误优先检查固定配置，偶发错误再看资源峰值、连接状态和时间变化。修复后既测正常路径，也验证启动失败、依赖不可达与重启条件，避免只在已有运行环境中成功。

## 五、适用边界与结论

静态 IP 不解决物理链路或认证，不能用反复拔插代替根因定位。

这条路径把“记录链路与内核事件”与“持续测实际业务路径”连在一起，中间保留可复查的条件。实施时优先确认“拔插前后变化可解释”，再检查“无重复地址与网关冲突”；两者都满足，才能在当前样本与配置范围内评价方案。设备、数据或软件版本改变以后，相关假设需要重新验证。
